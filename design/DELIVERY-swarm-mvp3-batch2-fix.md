# 交付 · 群研 MVP-3 第二批补修（B12 插话打挂负责人 / B11 运行挂了还显示运行中）

分支 `codex/swarm-3`，一个提交。契约 13 没改；前端（`02a3d69`）没动。

## 原因

`mention` / `redirect` 和批卡后的指令都是「先写回执，再 `kernel.submit(...).catch(() => undefined)`」。负责人那一轮还在跑时，`submit` 又给它起了一个回合 → 同一会话两个回合，两个一起 `failed`；之后 `submit` 报 `RUN_NOT_STARTABLE`，而错误被 `.catch` 吞掉，回执照写「已投递 / 已执行」。

## 改法

**1) 负责人忙就排队，在它的下一个步骤边界送进去（不另起回合）**

- 新表 `swarm_inbox`：`target`（`lead` 或队员名）、`kind`、`text`、`intervention_id`、`state`（`pending / delivered / applied / failed`）。
- `mention` / `redirect` / 批卡后的指令：负责人有回合在跑（`kernel.isLive`）就只入队，回执写「负责人这一轮还在跑：已排进它的收件箱，下一步边界送到」。
- 送达点是**负责人下一次调用工具的返回**：`/kernel/tool` 在 `dispatch` 之后把该目标的待送条目并进结果（`userMessages` + 一句说明），并把条目记 `delivered`。队员的工具按 `args.member` 归属，`swarm.plan/meta/status/log` 归负责人——不会把给负责人的话塞进队员的结果里。
- 负责人空闲时仍然起一轮，但这次**等真实结果**：成功才记 `delivered`，失败就 `failed` 并写原因。

**2) 回执按真实结果写**

- `add_member`：批准只到 `received`（「等负责人在下一个步骤建人」）；**名册真的多出人来**（`membersAfter` 达到）才写 `applied` +「已建出队员：现在名册里有 N 名成员」。
- 送不进去：干预写成 `failed`，`result` 里是具体原因；批卡的返回也如实写「已批准，但没能把指令送进去（原因）」。
- 这三条路径里不再有 `.catch(() => undefined)` 吞错。

**3) 负责人的运行挂了 → 群研转「已暂停」（B11）**

- 内核的 `onState` 在群研模式下、回合不是正常结束时调 `onLeadTurnFailed`：把群研标成 `paused`、写清原因（额度 / 网络 / 其它各自一句）、推一条系统说明与新的阶段结果；活动时长照样结算，不清零。之后成员各自跑完也不会让页面继续显示「运行中」。
