## B14 两件事

**1) 加人指令真的送到负责人**

之前 `decideCard` 走的是「`enqueueMessage` 写一行 + `kernel.submit` 起一轮」的老路：负责人忙时起不来，
那行就一直 `pending`，而回执照写「已执行」。现在和 `@队员` / `改方向` 同一条路——`deliverToInbox`
把指令排进**负责人的原生收件箱**（`session/prompt`，`mode=steer`，下一步边界送到），
回执按真实结果写：「指令已排进负责人的收件箱（下一步送到）」或者把失败原因写出来。

**2) 「已执行」要能对上这张卡建出来的人**

- 批准那一刻把当前名册 id 存进卡里（`approvedMemberIds`）。
- 之后只有在「批准之后新出现、且角色与本卡一致（卡上给了路线就还要对上路线）」的成员出现时，
  才把干预写成 `applied`，并写明是哪个人：`已按这张卡建出研究员 r4-gapfill（r4-gapfill）`。
- 只数人头的老判定删掉了（`project()` 里那份重复的旧代码也删了——它在真机上抢先生效，
  回执里还出现「现在名册里有 N 名成员」的旧文案）。

## 顺手：给负责人的插话排到 next-step

`kernel.queuePrompt` 改成走 JSON-RPC 的 `session/prompt` 并带 `mode: "steer"`
（运行时的入参形状是 `{ request: { requestId, sessionId, mode, content } }`）：
`steer` = 下一个步骤边界就到，`queue` = 下一轮。用户插话、改方向、加人指令都用 `steer`。
运行时若不认这个形状，自动退回 SDK 自带的 `prompt()`（下一轮），回执不会假装送到了。
