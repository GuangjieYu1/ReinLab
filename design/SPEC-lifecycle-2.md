# SPEC · 第 2 项 运行生命周期

日期：2026-10-29。依据：[PRD 02 第 2 项](../prd/02-foundation.md)、[WORKFLOW](../WORKFLOW.md)。
分支：`codex/lifecycle-2`（从 `main` `7992266` 起）。

## 1. 现状（已核对，不是假设）

| 事实 | 位置 |
|---|---|
| 等人点卡是插件内轮询，最多 600 秒，到点把卡标过期 | `plugins/reinlab-read-plugin/index.js` `awaitDecision` |
| 等待期间会话租约已由控制面放开，但内核进程与该轮仍活着 | `services/control/src/api/kernel-tools.ts` `lease_run_id=null` |
| 业务请求会「十分钟后过期」，过期后原任务按失败/停止收尾 | 同上 + `approvalTimeoutMs: 600000`（`kernel/dsh/launch.ts`） |
| `cancel` 可能返回 `cancel_unconfirmed`，之后需人工处理 | `services/control/src/kernel/service.ts` `cancel` |
| 没有启动核对：进程已死而 run 仍 `running` 会一直挂着 | 全仓无 reconcile 入口 |
| DSH 原生 `plan-mode` / `user-questions` 在依赖里可用 | `node_modules/.pnpm`（`0.2.1-rc.4`） |

结论：PRD 2.8 点名的「插件阻塞轮询等人」「统一十分钟判过期」「残留需人工释放」三条都在，是需要改掉的东西。

## 2. 目标状态（对应 PRD 2.3 状态表）

- 等待**没有业务有效期**：只有用户停止、请求被替代、动作已不适用三种情况关闭请求，并写明原因。
- 等待时**释放执行段**：安全结束该轮、确认不再写会话后，进程与写入权让出；不是只删租约让旧进程继续写。
- 回答后**续接原会话**：先持久保存回答，再按原生机制把回答关联回原请求；原调用已结束就走后续轮次，不补造工具结果。
- 失败/停止**有限时间内自动收尾**：run 必有终态，不会再出现需要人工 SQL 的 `cancel_unconfirmed` 常态。
- 服务启动**核对未终结工作**：进程已退出的 run 自动补终态、清占用与失效请求。

## 3. 改动（按片交付，逐片测试）

### 3.1 片一：去掉业务过期，等待不再自动作废

- `requestApproval` 产生的卡与提问不设过期；删除 `awaitDecision` 的 600 秒截止与 `expireCard` 的自动调用。
- 保留 `/kernel/approvals/:id/expire` 仅供「请求被替代」内部使用，不再由超时触发。
- 前端 `approval.expired` 仍可展示，但不再由等待时间产生。

测试（`kernel-tools.test.ts` 等）：等待超时后卡仍 `pending`；同一动作不因时间推移产生新卡或 409。

### 3.2 片二：等待释放执行段

- 插件遇到需要用户决定时，**立即返回 pending** 结束该轮，不再轮询；内核进程正常退出。
- 控制面在收到 pending 时记录「等待请求」（见 3.4）并释放租约；确认该轮已不再写入后才允许下一段取会话。
- 不允许「只把 `lease_run_id` 置空、旧进程继续写」。

测试：等回答期间 `dsh_session.lease_run_id` 为空且无活跃子进程；下一段工作能取到会话。

### 3.3 片三：回答后续接

- 新增回答入口：写入回答 → 关联原请求 → 以「回答」为输入恢复同一 session 的下一段执行。
- 原调用仍在原生等待内时走 `userQuestions` 回答路径；已结束则作为后续消息送入，不伪造工具结果。
- 计划确认绑定实际审阅的计划版本；计划变更不自动沿用旧批准。

测试：同一 session 续接（不新建空会话）；回答只生效一次；重复提交幂等。

### 3.4 片四：收件箱统一承接（最小语义）

服务端新增一张请求/报告记录（标识、账户、来源工作台/档案/任务、类型、内容引用、可用操作、状态、回答、关联）。原工作台与收件箱读同一份状态，不各维护一份。

测试：同一请求在原页与收件箱状态一致；处理后不残留待批卡。

### 3.5 片五：失败、停止与启动核对

- 启动、模型请求、工具调用、进程停止都有有限的执行时限；等待人回答不计入。
- 启动时核对待终结 run：进程已退出则按真实情况补 `completed`/`failed`/`interrupted`，关闭失效请求。
- `cancel` 在有限时间内自我确认；超时也要落终态并给出真实原因，不留人工步骤。

测试：构造「进程已死、run 仍 running」，启动后自动收尾；取消必定收敛到终态。

## 4. 执行时限与收尾配置（PRD 2.6 要求公开默认值）

| 名称 | 默认 | 含义 |
|---|---|---|
| `KERNEL_TURN_TIMEOUT_MS` | 待定（按实测正常精读留足） | 单轮执行上限，等待回答不计入 |
| `KERNEL_STOP_GRACE_MS` | 待定 | 请求停止到判定收尾的宽限 |
| `LOCAL_RECONCILE_INTERVAL_MS` | 待定 | 运行期轻量核对周期 |

具体数值在实现片五时按真实流程实测后写入本 spec 与启动输出。
