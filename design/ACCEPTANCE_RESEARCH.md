## 1. 原则

1. **自己复跑，不只看报告。** Codex 提交的测试报告只作参考，所有自动化套件由验收方在 staging 与本地重新执行。
2. **抽查超出测试。** 场景验收里的数值核对、引用核对、越权尝试，由验收方另选样本，不使用 Codex 自测用过的样本。
3. **结论看证据。** 每一项都要有：命令、输出、截图或录屏、账本导出中的至少一种。
4. **红线一票否决**（第 3 节）。

## 5. 场景验收（对应 PRD 的四条成功标准）

### 5.1 SC-READ · 精读一篇 arXiv 论文

**样本：** 主样本是 arXiv `1706.03762`（Attention Is All You Need，开放获取）。验收方还会另选一篇数学类 arXiv 论文作为第二样本，开始验收时才告知。

| 步 | 操作 | 判定 |
|---|---|---|
| 1 | 新建研究档案，输入 `1706.03762` | 显示费用预估（¥、额度、GPU 三栏），默认预算 ¥5 |
| 2 | 开始精读并计时 | **2 分钟内**出第一层；**10 分钟内**出全部层 |
| 3 | 抽查 10 条数值说法（验收方自选，例如各项 BLEU、模型维度、头数、训练步数、硬件与时长） | 10 条都能点回原文，页码正确，引文在该页能找到。**10/10 才算过** |
| 4 | 抽查 5 条非数值说法 | 作者声称与助手解读区分正确；解读类不得冒充原文 |
| 5 | 从「方法」层的一段原文发起提问 | 回答带出处；会话显示定位；换到另一段提问，定位随之改变 |
| 6 | 作答 2 道检查题（1 对 1 错） | 作答后才出解释；结果写进档案 |
| 7 | 对「缩放点积注意力」生成互动解释 | 生成成功，或按规格降级为静态图解；在沙盒 iframe 中运行；接受后挂到对应层 |
| 8 | 驳回一个动画并写原因，再生成一次 | 原因被用于再生成（在请求或账本里可见） |
| 9 | 查看复现提议 | 提议列出代码版本、数据、权重可得性、算力与费用、与原文的差异；**未批准前没有任何计算任务** |
| 10 | 用一篇付费墙论文的 DOI 新建精读（验收方现场挑选） | 标为「只有摘要」，并提示上传；不尝试绕过付费墙 |
| 11 | 收尾 | 升级提议（论文与批注）进入上线收件箱；不批准时 L4 中没有该论文 |

**通过：** 第 2、3、7、9、10 步必须全部满足，其余步骤不得出现 Sev1 / Sev2 缺陷。第二样本只要求第 2、3 步（抽查 5 条）通过。

### 5.2 SC-SWARM · 一次端到端群研

**问题：** 「长上下文场景下，检索增强（RAG）与长上下文模型直接阅读，各自的优劣与适用条件是什么？」
**预算：** 默认 ¥30。

| 步 | 操作 | 判定 |
|---|---|---|
| 1 | 请求编制提议 | 1 分钟内给出：子问题、人数（8–12）、角色配比、模型档、预计费用；**未确认不启动** |
| 2 | 把人数改为 10 后启动 | 实际编制为 10 |
| 3 | 运行中观察 | 7 种消息里至少出现 5 种；同时活跃的 agent 数不超过上限；排队在黑板上可见 |
| 4 | 运行中打开任意一个 agent | 能看到它的完整过程（输入、工具调用、输出） |
| 5 | 等待结束（或预算门禁触发后由验收方决定） | 结束原因写进账本 |
| 6 | 检查报告 | 每条结论都有出处与核实签核；验收方**随机抽 5 条引用**回到原文核对，5/5 通过 |
| 7 | 检查反驳 | 至少一条反驳记录，且结局是「补证据」或「降级为局限」之一 |
| 8 | 检查负结果 | 有负结果单列，或明确写「无」并附检索记录 |
| 9 | 回放：拖到 3 个时刻（25% / 50% / 90%） | 重建的任务板、黑板、在途消息，与账本在该时刻的状态一致（验收方用账本自算比对）；回放期间不产生模型费用 |
| 10 | 费用 | ≤ ¥30，或每次超支都有对应的追加批准记录 |
| 11 | 收尾 | 核实过的结论与负结果的升级提议进入收件箱 |

**通过：** 第 1、6、9、10 步必须满足，其余步骤不得出现 Sev1 / Sev2 缺陷。

### 5.3 SC-AUTO · 自研跑通 OCR 例子

**数据集**（Codex 提供，放在 `infra/fixtures/ocr/`）：
- 50 页扫描风格的图片或 PDF：用公有领域的中文与英文文本渲染后，加入噪声、倾斜、模糊、低分辨率；
- 每页附标准答案文本；
- `README.md` 说明生成脚本，保证可再生成；
- 另留 10 页作为**验收方的留出集**，Codex 的运行不得使用。

**目标：** 字符准确率（1 − CER）≥ 98%。预算由验收方在开始时设定。

| 步 | 操作 | 判定 |
|---|---|---|
| 1 | 不提供评估集，直接启动 | 被拒绝，返回 `NEEDS_EVAL_SET`，并给出抽样标注入口 |
| 2 | 抽样标注（用数据集自带的标准答案提交 20 页） | 评估集登记成功 |
| 3 | 完成研究简报 | 问题、假设、指标（含计算方式与方向）、范围、预算、算力齐全，保存为 `program.md` |
| 4 | 启动 study | 先跑基线并记录；之后每个想法一次运行，带「保留 / 回滚」判定 |
| 5 | 观察前沿曲线与运行矩阵 | 和 `results.tsv` 一致 |
| 6 | 下一条常驻指令（例如「只尝试预处理」） | 之后的想法遵守该指令，直到撤销 |
| 7 | 结束（达标或预算用完） | 报告给出最优配置、关键消融、lessons |
| 8 | **独立复现：** 验收方按报告里的最优配置，在留出集上单独运行 | 准确率与报告里评估集的数值相差 ≤ 1.5 个百分点（防过拟合评估集） |
| 9 | 收尾 | lessons 的升级提议进入收件箱，注明适用场景与证据运行 |

**通过：** 第 1、4、7、8 步满足。**是否达到 98% 不作为通过条件**：循环必须正确地在达标或预算用完时停下，并如实报告结果。

### 5.4 SC-DELEG · 接住课程台的一次调研委托

| 步 | 操作 | 判定 |
|---|---|---|
| 1 | 在课程台档案「群论 · 对称与群」里，只批准「调研」这一段 | — |
| 2 | 课程台发出 `research_request@1`（问题：群论自学的方法与路线；预算 ¥8；期望 `research_findings@1`） | 请求通过 schema 校验 |
| 3 | 研究台选模式 | 选为群研，理由写进账本 |
| 4 | 结果交回 | 通过 `research_findings@1` 校验；`negatives` 非空，或明确写「无」并附检索记录 |
| 5 | 账本 | 两边各有记录，用同一个委托 id 能串起来；费用从课程台的预算里划出 |
| 6 | 边界 | 研究台**没有**做侦查、适配或任何下一段的工作；课程台的下一段仍是「可开始」，不是「执行中」 |

**通过：** 所有步骤满足。

## 6. 安全检查（验收方亲自执行，不依赖 T-SEC 的样本）

| 编号 | 检查 | 期望 |
|---|---|---|
| SEC-1 | 用账户 A 的 JWT 访问账户 B 的档案、运行、事件、论文、群研、升级请求、委托：每个 API 各试一次，并换 id 再试 | 全部 403 或 404，**0 行数据泄露** |
| SEC-2 | 直接用应用连接查 B 的表（模拟应用层漏洞） | RLS 返回 0 行 |
| SEC-3 | 在账户 A 的容器里，用 B 的会话 id 调 `/internal/os/tool-call` | 拒绝 |
| SEC-4 | 通过页面、聊天指令、直接 API、插件工具四个入口尝试 danger 动作（删除档案） | 四个入口全部无法执行；只有界面上的人工操作可以 |
| SEC-5 | 构造恶意互动 HTML（读 `parent.document`、`document.cookie`、`localStorage`、`top.location=`、提交表单、`window.open`），走动画渲染路径 | 全部失败；或在 HTML 校验阶段被拒并降级 |
| SEC-6 | 在 SSE、日志、账本、证据目录里扫描凭据模式（API key 前缀、Bearer token、OAuth refresh token） | 0 命中 |
| SEC-7 | 让一个搜索 agent 调用核实者专属的签核 | 被拒，错误码 `SCOPE_DENIED` |
| SEC-8 | 从公网直连账户机器的 4096 端口 | 不可达 |

## 7. 可靠性检查（故障注入）

| 编号 | 注入 | 期望 |
|---|---|---|
| CH-1 | 群研进行中重启账户机器 | 运行被对账为 `interrupted` 或续跑；不重复已发生的工具副作用；账本无重复事件（`dedupe_key` 唯一） |
| CH-2 | 杀掉 Hatchet worker，再恢复 | 工作流从最后一个检查点继续 |
| CH-3 | 客户端断网 30 秒再恢复 | SSE 用 `Last-Event-ID` 续读，事件不丢不重（序号连续） |
| CH-4 | 在审批待决定时重启 OpenScience 进程 | 原审批标为 `expired`；界面提示，不显示可点的「批准」；不自动重提 |
| CH-5 | 同一个 `Idempotency-Key` 用不同内容重发启动运行 | 返回 `IDEMPOTENCY_CONFLICT`，没有第二个运行 |
| CH-6 | 预算正好用完时并发两个工具调用 | 最多一个越过门禁，且账本记录超出的金额与原因 |

## 11. 缺陷分级与处理

| 级别 | 定义 | 对结论的影响 |
|---|---|---|
| Sev1 | 命中红线；安全或数据泄露；重复副作用；伪造验证 | 不通过 |
| Sev2 | 任一 P0 项不达标 | 不通过 |
| Sev3 | P1 项不达标；明显的体验问题 | 可「有条件通过」，需附修复计划与期限 |
| Sev4 | 文字、样式等小问题 | 不影响结论，记录在案 |

**复验：**
- 缺陷修复后，只复跑受影响的检查项，加上全部 T-REG 与 T-SEC。
- 红线类缺陷修复后，必须重跑整个第 6 节与第 8 节。
- 复验轮次不设上限，每轮都单独出报告。

## 12. 结论与报告

**结论三选一：**
- **通过**：P0 全部通过；P1 通过率 ≥ 90%；无未关闭的 Sev1 / Sev2；四个场景全部通过；证据齐全。
- **有条件通过**：在上面的基础上，存在 Sev3，且修复计划已确认。
- **不通过**：其他情况。

验收方产出 `evidence/final/ACCEPTANCE_REPORT.md`，结构如下：
1. 结论与日期、被验收版本（提交号、镜像标签、OpenScience 版本）。
