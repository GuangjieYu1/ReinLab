## 1. 要做成什么

群研承接用户研究问题，以及学习的课程调研、工程的算法路线、数据的结果分析、设计的考据委托。用户确认问题、路线、编制和运行额度后，团队独立探索、交叉借鉴、反驳、核实，交付有出处的结论和精确缺口。没有找到也是结果。

沿用任务树、通信、留言板、汇总四个面。现有 `src/components/workbenches/research/swarm/` 是定时模拟剧本，人数、消息、暂停和报告均不代表真实运行。真实版本从实际事件驱动；本批不改前端样式和交互。

## 2. 运行底座与已核实的兼容性

**选择：保留 DSH `0.2.1-rc.4`，搭配同版本官方团队插件，无需因群研升级。**

2026-11-02 核对 `infra/account/Dockerfile`、`pnpm-lock.yaml` 和本机实际安装包：`@deepseek-ai/dsh-experimental-agent-team`、`@deepseek-ai/dsh-experimental-tool-agent-team`、`@deepseek-ai/dsh-experimental-agent-team-profile` 均有 `0.2.1-rc.4`；团队与工具包对 DSH 核心的 peer dependencies 精确要求 `0.2.1-rc.4`，Cordis 要求 `~4.0.5`，本机符合。官方对应 tag 的说明已包含直接收件箱、冷恢复、持久任务板、版本校验与保留收件箱的中断。

依据：[同版本官方团队说明](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.4/packages/experimental/agent-team/README.md)、[团队包声明](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.4/packages/experimental/agent-team/package.json)、[工具包声明](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.4/packages/experimental/tool-agent-team/package.json)。不混装 master 的 `0.2.2-alpha.2` 或镜像站过旧的 latest。

验证边界：这是发布包依赖与同版本能力核实；当前没有运行中的账户容器，尚未证明 ReinLab 配置已加载团队插件或真实建队成功。DSH 实现首步应在实际账户容器加载同版本插件和持久会话存储，真实建队、发消息、领取任务并恢复一次。失败先定位配置或调用差异，不先升级或另起运行时。

官方 agent-team-profile 可作为插件组合配置的参考；正式接入由账户容器的既有加载方式启用同版本服务与工具。方案中的 Web profile 安装命令和官方 UI 只用于理解组合，不作为 ReinLab 产品入口，不要求用户切换 DSH Web/Desktop 或安装另一套界面。

团队扁平，只有负责人建队；逻辑研究小组用标签。默认负责人 1、研究员 3、反驳 1、核实 1，拆解和汇总由负责人承担。研究员可兼做检索、阅读、分析，不要求旧版八种角色各占一个人。

用户本轮确认覆盖 11 的人数歧义：完全沿用 DSH `maxMembers=16`，即负责人 + 累计最多 16 个队员；失败创建也占名额，名字不复用。中途加人仍需审批，触顶说明原因，不悄悄新建团队绕过。

## 3. 澄清、轮次与收尾

- 澄清由负责人评估问题边界、质量判据、不同路线、人员与模型、轮数和时长。计划额度最少 **4 轮 / 30 分钟**，复杂问题按需提高；开跑前一起确认。额度下限不是强制耗满，已有充分核实的答案可提前结束。
- 一轮是负责人发布一批研究任务，收齐产出或明确失败/阻塞后，综合、质疑并调向一次；不是模型的一次调用，也不是每人必须同步结束。每个任务带轮次与计划版本，迟到产出保留原归属。
- 用户已确认：前 2 轮独立探索，从第 3 轮开始交叉借鉴，按需开放已提交产物。早期负责人可比较路线，但不向研究员透露“领先答案”；反驳与核实可读取被审材料。
- 时长从确认开跑起计，包含工具执行和收尾；整个团队暂停期间不消耗活动时长额度。用户已确认：全队等待用户时暂停活动计时，浏览器断线继续计时。仅一条路线等待时，其他路线继续、计时继续。
- 额度内自动推进。临近上限展示“新发现、剩余缺口、建议追加多少”；用户确认追加才继续。轮数或时长任一到限就停止新增研究任务，中断仍运行的探索，保存阶段结果。收尾不得偷偷延长模型调用额度；不足以生成新报告时展示已有核实结论和未完成项。
- 可提前收尾：问题已回答且通过核实；全部剩余路线明确阻塞且没有实质新机制；用户要求结束。失败一轮不等于整个研究失败。依赖外部材料或人的问题可暂停受影响路线，全部无法前进才暂停团队。
- 用户本轮明确：**群研运行及真实验证均只记费用，不按费用拦截**，覆盖 AGENTS.md 对本功能的付费预算上限。按峰值费率估算，未知用量标未知；仍遵守 key 仅在进程内存读取、不进入环境变量、argv、日志和聊天。

## 4. 任务合同、研究黑板与任务板

任务合同最少包含：研究问题和边界、必要背景、路线及与其他路线的区别、授权材料版本、具体产出要求、判断完成的标准、负责人/执行者、轮次和计划版本、可见范围、停止条件。只把合同和必要背景交给全新上下文的研究员。

合同固定关联 run_id、task_id、route_id、contract_version 与依赖任务；产出必须明确区分来源主张、研究推断和实际观察，列出适用条件及剩余缺口。文献任务交原文定位，计算任务交代码/输入版本与实际结果，证明任务交命题、假设和可检查证明。格式校验只证明交付完整，不代表内容通过核实。

对齐实现方案的合同语义：`variantId` 表示问题变体，`approachFamily` 对应路线方法族，`contextMode=fresh`、`allowedContext`、`independentExploration` 明确上下文与访问范围，`expectedOutputs` 和 `stopWhen` 明确产出与停止条件。TaskContract 是 ReinLab 自定义数据，适配器按锁定版本的真实参数生成初始任务，并维护研究任务与 DSH task/session 的映射；不能把合同 JSON 原封不动传给 `spawn_teammate`。

第 3 轮起跨路线迁移使用精简 Context Packet：目标任务、关联结论及版本、当前核实状态、来源定位、适用条件、局限与待解问题。未核实想法可作为明确标注的假设借鉴，不能包装成可靠事实；状态变化后接收路线查询最新版本。只转移授权的产物，不转移完整会话或他人的工作目录。公共决定仍写黑板，需特定成员处理的成果才用定向消息。

DSH 任务板唯一管理执行任务的身份、依赖、负责人、执行状态和版本；研究黑板管理研究含义。研究结论是否可靠不能从“任务完成”推断。

| 对象 | 最小内容 | 与任务板关系 |
|---|---|---|
| 研究运行 | 档案 ID、run_id、负责人 session_id/team_id、问题、计划版本、额度及已用量、轮次、独立/交叉阶段、运行状态 | 一个运行关联一个团队；恢复复用原团队 |
| 路线 | route_id、核心思路、不同点、标签、当前缺口、状态、重新开放理由 | 关联多个 DSH task_id；同义改写不能登记成新路线 |
| 问题/求助 | ID、问题、提出者、指定接收者或公开范围、关联任务、回答及 reply_to、待答/已答 | 人工阻塞关联审批卡；提问与回复可配对 |
| 证据 | evidence_id、原始来源/材料版本、页码/段落/代码位置、摘录或实测记录、取得方式、全文/摘要范围、访问状态 | 被具体交付和结论引用；来源打不开标缺口 |
| 交付/结论 | submission_id、claim_id 与版本、具体主张、适用条件、证据引用、负结果/剩余缺口、作者、可见范围 | 固定关联 task_id 和该次合同版本；可一任务交多条结论 |
| 反驳/核实 | review_id、目标结论版本、审查者、类型、理由、原始证据、判定、反驳轮次 | 反驳与核实为独立任务，分别关联 DSH task_id |
| 决定 | decision_id、决定内容、适用范围、计划版本、依据、发布人 | 广播落在这里，成员按需读，不扇出消息 |
| 研究事件 | event_id、run_id、对象 ID/版本、操作者、时间、事件序号、关联会话和工具调用 ID | 补足提交、审查、黑板、用户干预与任务变化的关联 |

留言板仍呈现问题、发现、求助、决定四栏；证据、路线、反驳作为关联对象展开，不把数据库对象都变成新的页面。

结论采用明确状态：候选、待反驳、待核实、已核实、有争议、已证伪、证据不足。正常路径是候选 → 独立反驳 → 独立核实 → 已核实；异议附具体对象、理由、证据与处理结果，不能只留一句“不同意”。已证伪结论保留撤回原因，证据不足保留缺口；“已阻塞”属于路线/任务推进状态，不与结论真假混在一起。证据标明已核对事实、来源作者宣称或研究推断，来源自称成功不能直接升级为已核实事实。

交付先持久保存并校验，再完成 DSH 任务；两步间断线显示“交付已存、任务状态待同步”，按 submission_id 幂等补齐，不能让模型重做。任务完成但没有合格交付不算研究完成。DSH 依赖与领取直接复用原子操作；版本冲突刷新任务，不覆盖他人修改。

路线卡在与原题同样难的归约或缺口上就标阻塞；只有登记具体新机制才可重新投入。路线按思路本质归类，过度聚集时负责人把后续任务调往不同路线。空泛进度不能充当交付；负结果须说明找过什么、范围及没得到什么。

## 5. 隔离与最小工具集

研究员只读写自己的工作子目录，并只读获授权的材料。负责人读各路线交付；反驳、核实按审查任务读所需产物和原始来源，不能修改研究员原稿。跨路线共享通过批准开放的不可变提交版本，研究员不直接浏览别人的工作目录。

这要由工具和存储层检查运行身份、路径与材料授权；路径规范化并处理符号链接。默认通用 bash、全盘搜索、文件读取和 MCP 若能绕过限制，则不得原样暴露给研究员，必须替换为受限入口。DSH 的 writeScopes 只是冲突提示，不能作为权限隔离。DSH 任务描述、消息、黑板查询也不得在独立阶段泄露别的路线答案；任务板只存任务元数据和合同引用，详细结果放受控黑板。独立阶段限制研究员间传递结论，向负责人、反驳、核实提交仍可用。

最小研究工具采用实现方案的建议名称，参数由后续 DSH 契约细化；这些是待实现的 ReinLab 工具，不是 DSH 现成接口：

| 研究工具 | 做什么 |
|---|---|
| 提交 `research_submit` | 按对象类型提交结论/证据/负结果、问题/回答、求助、决定；校验具体产出、引用和权限 |
| 查询黑板 `research_query` | 按角色、路线、阶段、任务过滤，按版本增量读取；分页返回有限数量相关条目及引用 ID，需要时再展开原文，不能只靠前端隐藏 |
| 登记路线 `research_register_approach` | 去重归类、标阻塞、记录新机制、申请重新开放 |
| 审查结论 `research_review_claim` | 分别记录反驳、补证据要求、独立核实及降级；绑定目标版本 |

创建成员、成员列表、任务增改查/领取/完成/依赖、定向消息、等待变化、中断直接复用 DSH 团队能力，通过研究权限检查，不复制另一套调度器。用户审批、材料检索、全文读取与定位复用现有服务。ReinLab 只补研究语义和多轮计划。

按实现方案分为三个 ReinLab 插件包：`reinlab-research-orchestrator` 负责轮次、合同、方法族分配、隔离策略和停止条件；`reinlab-research-blackboard` 负责 Claim/Evidence/Approach/Question/Challenge 的持久化、查询、来源关系与版本；`reinlab-research-verification` 负责反驳与核实任务、验证适配和结论门禁。三者共用研究对象 ID 与事件合同，执行任务始终归 DSH 任务板，不各建一套任务状态。

控制面采集事件、接入审批与跨台委托，向四个面提供统一投影；`reinlab-research-ui` 指现有 ReinLab 群研前端的接入模块，不另建业务后端，不嵌官方 Team UI。角色沿用 DSH preset 和工具权限配置。实现方案列出的官方工具映射（spawn_teammate、team_task_create/update/list/get、send_message、wait_agent、list_agents、interrupt_agent）由 DSH 在锁定版本中核对参数后直接适配，不按同名自建运行器。

首期按来源标识/材料版本/定位去重证据，并用路线登记与负责人判断避免重复派工，保留同源引用的关联；语义检索和近义去重后续完善，不作为真实首例的前置工程。检索前先按权限裁剪，返回摘要也不得泄露独立阶段其他路线结论。新增证据、未解决缺口和阻塞原因决定后续派工，不用消息数量或报告字数衡量进展。

每条候选结论都要查漏洞。反驳与核实分人分任务；核实者不能给自己的结论签核，必须检查原始材料而非复述反驳者意见。每条结论最多两轮反驳，改个版本不重置计数；之后仍有争议就呈现分歧，不能写成已证实。修改主张或证据后旧核实失效，重新核实当前版本。

核实随证据类型进行：文献回到原始出处；计算结论核对可复现的实际运行和输入范围，未运行不得称为已复现；数学结论检查命题、假设与证明，已有形式化材料时保留检查结果，未形式化不得宣称形式化验证。无需为所有研究任务引入新的证明器或执行框架；无法核实就保留缺口。Agent 共识和多数投票均不能替代这些依据。

最终报告正文的可靠结论必须有对应版本的独立核实；其他内容只能出现在明确标注的局限、争议、未核实和待确认区。用户可以决定如何继续，不能用审批替代事实核实。报告前仍有分歧就给用户看一眼；未答时保存待确认阶段结果，不悄悄宣告研究完成。

## 6. 用户干预与可见过程

| 用户动作 | 实际路径与可见回执 |
|---|---|
| @某队员 | 控制面记录用户指令 ID，向目标会话定向投递；显示已接收/待处理/已回复，不把进入收件箱称为已执行；普通留言不会自动泄露给其他路线 |
| 改方向 | 立即停止受影响任务，保存已有证据；负责人增加计划版本并自动继续。扩大原问题范围需确认，只显示新旧计划差异 |
| 加人 | 审批卡展示新增角色、路线、模型、人数变化；批准后由负责人创建；不绕过累计名额 |
| 停止路线 | 记录停止决定并中断该路线任务；中断不自动释放 DSH 归属，负责人显式处理任务与下游依赖。保留产出，依赖任务显示被挡住及原因 |
| 暂停/继续 | 暂停先停止派发并中断当前队员及负责人执行，保留收件箱、合同和产出；继续核对现状再启动，不重复提交已完成结果 |
| 结束研究 | 停止新工作，保存已有可靠结论、未完成任务和剩余缺口；明确显示部分完成或无法完成，不伪装成功 |

四个面应能解释“谁在做什么、为什么卡住、依据是什么”。任务树显示真实依赖与阻塞，成员显示所用模型、运行/空闲/失败等状态、全新/继承上下文；通信显示发送结果、提问回答、交付审查、版本冲突与中断；留言板显示研究对象；汇总可查看当前阶段结果，不必等所有任务成功。

点开队员查看实际可见工作记录：输入、工具、来源和输出，以及内核公开的摘要。回放和实时控制区分：拖动历史时间轴只读日志，不暂停后台研究，不触发模型。

## 7. 通信采集与断线恢复

服务端汇合各成员会话的发送工具调用及返回结果、接收方消息、DSH `agentTeam` 任务/成员投影和研究事件；保留原始会话序号，按统一事件序号提供稳定时间线，不能把不同时钟时间戳当因果关系。发送失败也可见；返回 inbox message_id 只说明接收成功，处理状态来自后续真实事件。研究侧用关联 ID 去重，不假设 DSH 会替显式重发去重。

恢复锚点：run_id、lead/team session_id、成员 session_id、每个会话最后事件 seq、研究事件游标、task_id/revision、submission_id、当前轮次/计划版本、审批状态、活动时长累计。断开浏览器只是断开观察；重连先取当前快照，再补游标后的事件。

## 8. 精读与跨台委托

用户已确认：研究员直接复用精读的检索、取全文、定位及引用能力；用户需要完整讲解、批注或继续精读时才建立关联精读任务。两边共用材料的固定版本和定位，分别保留会话；精读已有解释不是群研独立核实的替代品。精读结果返回对应任务和结论，原运行已结束则作为后续版本，不能悄悄改已发布报告。

委托输入最少为：`delegation_id`、源/目标台、源档案、明确问题、背景摘要、授权材料及版本、期望产物、用户约束、确认记录。确认后幂等创建研究档案和目标任务；目标只读授权引用，不继承源档案全部记忆。澄清可与委托确认合成一次，但运行计划没确认就不开跑。

委托输出最少为：原 `delegation_id`、研究档案/run_id、完成/部分完成/无法完成、结论及核实状态、证据定位、产物版本、局限、待确认问题、完整过程链接。源档案收到一张结果卡；重复回调更新同一卡，后续结果保留版本。用户在源档案决定采用，不直接覆盖源内容。

群研向工程、数据、自研等交出后续任务同用此合同，先确认范围和引用；普通检索、读材料不产生跨台委托档案。不同台无需首期都做新交互，但合同应覆盖四个委托来源。
