### 1.4 合并与运行要求

1. 在 `codex/foundation-unify` 通过正常 Git 合并纳入两个 `slim/*` 分支，保留双方历史；不通过整目录复制或强制选一边覆盖完成合并。
2. 冲突按功能处理：界面保留 Claude 的最终效果，后端保留已验收 DSH 实现；`main.tsx`、`src/data/`、`ReadMode.tsx`、依赖和启动配置联合核对。业务冲突按现有前端契约解决，不趁机改体验。
3. 统一使用 pnpm workspace、项目 Node 22 和 pnpm 锁文件。安装、构建、开发测试和启动入口统一；相应 README/CI 若仍引用旧包管理或路径则一并对齐，其他无关重构不做。
4. 根目录一条命令 `pnpm local:up --real-models` 启动整栈。前端、控制面与插件都使用当前 checkout 的源码/构建产物，不引用另一个工作树，不要求 Claude 再启动一份外部前端。
5. 延用现有 Node 22 启动修复，不因为从不同终端启动而误用 Electron 内嵌运行时。
6. 保留现有账号、Provider 配置与业务数据。本轮不是 PRD 01 的一次性清空，不再清空或重建数据。若本地实例标识/数据路径依赖 checkout 路径，迁入主目录时须保持现有数据可达，不能静默创建一个空实例代替原实例。
7. Claude 先验收集成分支，三方无问题后合入 `main`，主目录切到 `main` 成为日常入口。用户此前已同意合并 B1～B4；本轮集成结果仍依 WORKFLOW 验收后落主线。
8. 原工作树和旧分支停止作为运行/同步源。不为实现“单主线”直接删除尚有用户改动的工作树；后续清理不属于本轮验收前置条件。

普通功能分支与临时工作树仍允许使用。“一条主线”指唯一集成和交付基线，不要求多个 agent 同时修改同一 checkout。

### 1.6 实施与交付

DSH 按 spec → TDD → 实现 → 自审 → 测试推进集成。对确有变化的确定性行为补必要测试；纯 Git 合并或目录归属说明不为凑 TDD 新增测试。运行项目构建与适用开发测试，报告实际结果；发生回归则修复，不顺带扩充边缘场景矩阵。

交付说明只需：集成分支/提交、冲突处理要点、一条启动命令、构建与测试结果、Claude 的页面验收入口。精读真实调用额度按本轮实际授权执行，不自动继承 PRD 01 的额度。
