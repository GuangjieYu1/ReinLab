# 11 · 研究台群研 · 用户体验结论（用户与 Claude，2026-11-02）

为什么先做群研：别的工作台需要"去查清楚 X"时，都委托给研究台群研（学习→课程调研、工程→算法路线、数据→结果分析、设计→考据）。群研通了，后面各台的委托就有落点。

参考：astra 的调研报告与实施规格（用户转交）；PRD_RESEARCH_BENCH.md 第 7.3 节（OpenScience 时期的旧设计，角色与消息语义可沿用，运行方式按本文件改）；DSH_WORKBENCH_DESIGN.md 第 3、11 节（研究台与跨台委托）。

## 1. 已定

| 项 | 结论 |
|---|---|
| 运行底座 | DSH 官方 Agent Team 插件（`dsh-experimental-agent-team` / `-tool-agent-team` / `-agent-team-profile`）负责建队员、收件箱、任务板、等待与中断；ReinLab 研究插件只补研究语义（研究黑板、路线登记、反驳与核实、多轮推进）。不引入 LangGraph / CrewAI / AutoGen 等第二套运行时。版本是否与账户容器里的 DSH `0.2.1-rc.4` 兼容，DSH 先核实 |
| 团队形态 | DSH 团队是扁平的，队员不能再建子团队；"研究小组"用标签逻辑分组，所有队员由总负责人创建 |
| 默认编制 | 总负责人 1 + 研究员 3（全新上下文，各走不同路线）+ 反驳 1 + 核实 1，约 6 个；先跑通再加人。总负责人按问题提议编制，开跑前用户确认；中途加人走审批卡 |
| 隔离 | 研究员用全新上下文，只拿到任务合同和必要背景；"全新上下文"只隔离对话，不隔离文件，所以"早期不互看结论"要在 ReinLab 的检索和存储层限制 |
| 界面 | ReinLab 自己的界面（不嵌 DSH 自带 Web UI），沿用现有群研四个面：任务树、通信、留言板、汇总；能点开任一队员看它的工作记录。数据全部来自真实事件：DSH 会话事件 + 研究事件日志（DSH 团队目前没有统一的消息时间线，要补采集） |
| 什么时候问用户 | ① 开跑前确认问题、路线和编制；② 研究中遇到必须由人回答的问题，发审批卡到收件箱；③ 最终报告前，有没解决的分歧给用户看一眼；④ 其余全程自动，跑完通知 |
| 结论门禁 | 进最终报告的结论必须过独立核实（看原始来源、代码、证明，不看谁吵赢）；反驳与核实是两个独立任务，每条结论最多反驳两轮，超了标"有争议"交总负责人；被反驳的要么补证据，要么降级为"局限"；"没找到"作为负结果交付 |
| 委托 | 别的台发委托 → 用户确认 → 自动建研究档案并带上问题、背景、授权引用、期望产物；跑完给源档案回一张结果卡（完成 / 部分完成 / 无法完成 + 结论 + 证据 + 局限 + 待确认），采不采用由用户在源档案决定；研究档案保留完整过程 |
| 第一个真实案例 | "多 Agent 数量增加是否一定提高研究质量？"（能同时演示多路线、矛盾证据、反驳、核实、用户中途改方向） |

## 2. 借鉴金山木提示词的群研规则（核心）

来源：<https://github.com/jinshanmu/CrouzeixConjecture/blob/main/crouzeix_conjecture_prompt.txt>（原文是证明 Crouzeix 猜想的提示词，场景是数学证明；我们借的是组织多 agent 的机制，不照搬"禁止上网""假设一定有解"）。这些规则落在**程序状态和工具**里（路线登记表、阻塞状态、交叉借鉴时机、产出格式校验），不是写一大段提示词教模型。

1. **多样路线起步**：开局铺开真正不同的路线（不同表述、视角、方法），不按"每条路线固定 N 人"分配，按进展动态调配。
2. **早期独立**：前几轮大多数研究员不知道当前被看好的路线，避免一起收敛到一个漂亮但不完整的思路。
3. **路线登记表**：按思路本质归类（不是措辞）；太多人收敛到同一路线时，把一部分调往冷门路线。
4. **不让漂亮的归约霸占**：把问题归约成同样难的子问题，不算接近完成。
5. **阻塞标记**：路线卡在和原题同样难的缺口上，就标"阻塞"；只有有人提出实质性的新机制，才重新派人。
6. **多条互不相容的路线并存几轮**：各自发展到能看清强项和缺口后，再交叉借鉴。
7. **全程对抗审查**：每个候选结论都查漏洞、隐含条件、含糊带过、循环论证。
8. **只收具体产出**：引理、构造、数据、反例、可打开的出处；拒收进度汇报和空泛乐观（工具层校验交付格式）。
9. **总负责人反复综合、质疑、调向、开新一轮**：第一波失败不收手，在用户确认的轮数 / 时长内继续。
10. **收尾口径**：有通过审查的完整结论就交；没有就交"最强的严格结论 + 精确的剩余缺口"，不交"尽力了"式总结。

另：网传"一万个子 agent、88 小时攻克千禧年难题"确有其说，但内部方法未公开，不借鉴。

## 3. DSH 团队插件的通信机制与我们前端的对应（2026-11-02 定）

依据：DSH 官方仓库 `packages/experimental/agent-team`、`tool-agent-team`、`agent-team-profile`、`client-ui-agent-team` 的说明。

**DSH 原生**：点对点消息（进对方收件箱，运行中在步骤边界插入、空闲则唤醒 / 冷启动；对方看到的是"Team message from 某某:"开头的用户消息）；持久任务板（标题、详情、依赖、负责人、版本校验、改同一批文件的提示，总负责人可指派）；等待团队变化；总负责人打断队员（保留收件箱和任务归属）；成员生命周期（创建中 / 运行中 / 空闲 / 失败，全新或继承上下文，名字不复用）。**没有**：广播、公共留言区、提问—回答配对、结构化交付、反驳、通信时间线（消息存在接收方会话里，团队记录只有成员和任务）。

| 我们的消息 | 落法 |
|---|---|
| 领取 | DSH 任务板（原子领取、依赖未完成不能领、版本校验） |
| 转交 | 任务依赖 + 一条点对点消息 |
| 提问 | 点对点消息 + 研究事件里给提问编号，回答带编号配对 |
| 交付 | 研究插件"提交"工具（结构化结论 + 引用，校验格式）+ 任务标完成 |
| **广播** | **发到研究黑板"决定"栏，成员按需读；不逐个发消息**（用户定：省上下文、不打断人） |
| 求助 | 研究黑板"求助"栏 |
| 反驳 | 研究插件"审查结论"工具，状态：补证据或降级为局限 |

**通信时间线必须由服务端拼**（前端"通信"面的数据源）：各成员会话里"发消息"工具调用（发送方视角）+ 任务板变化（`agentTeam` 投影）+ 研究工具事件（提交、反驳、核实、黑板），按时间合并成一条通信流推给前端。

**前端要补显示的**（DSH 有、我们没有）：成员状态与所用模型；任务依赖与"被挡住"；任务版本冲突（说明没有重复劳动）；总负责人打断了谁；点开队员看它的完整会话（搜了什么、读了什么、怎么想）；每个队员是全新起步还是继承上下文。

**用户定的另外两条**：
- 人数上限 16（DSH 默认值，不改）；默认编制仍是约 6 人。
- **子目录隔离**：每个研究员只能读写自己的子目录，总负责人、反驳、核实按角色读需要的部分；DSH 团队共用工作目录，这层限制要由 ReinLab 插件 / 工具层落实（不只靠提示词），PRD 写清做法。

## 4. 留给 PRD 定的

- 轮数、时长的默认上限和停止条件（DeepSeek 便宜，花费只记账不拦截，但时间和"看得懂"要有边界）。
- 研究黑板的数据结构：结论 / 证据 / 路线 / 问题 / 反驳，与 DSH 任务板的对应关系；断线恢复锚点（task_id、已交付、轮次）。
- 研究工具最小集（astra 提议：提交、查询黑板、登记路线、审查结论），哪些可直接用 DSH 团队工具代替。
- 用户中途干预：@某个队员、改方向、加人、停止某条路线，各自走哪条路径。
- 与精读的衔接：群研需要细读某篇时，是派精读子任务还是研究员自己读。
