# 29 · 创作台的设定顾问、写作助手改成 DSH 模式 · 给 DSH 的开场

日期：2026-11-09。用户原话：「我们所有的助手/顾问都是拿 deepseek harness 来的，可以理解为 DSH 创造的一个模式，有不同的工具、不同的共享上下文，但基本 DSH 要有的东西都要有。」

## 现象 → 断点 → 期望

**1. 顾问没有上下文。**
- 现象：在顾问里接着上一句问，它不知道上一句说过什么。
- 断点：
  - `assistant-run.ts` 开头写明了「这一批不把它塞进内核容器……在控制面里跑」；
  - 页面每发一句都调 `POST /v1/kernel/runs` 新建一条运行；
  - `advisor.ts` 是一次性的结构化调用：系统提示词加设定摘要，只输出 JSON。
- 期望：顾问、写作助手都是真的 DSH 模式。
  - 同一个会话可以连续多轮，页面发下一句时续在同一会话里；
  - 压缩、工具调用、事件流这些 DSH 的基本能力都要有，和研究台的 agent 一样。

**2. 回复难读。**
- 现象：
  - 疑点、检查结果都用「；」连成一大段；
  - 每条回复都把整个世界观的全部红色冲突抄一遍，和这次提议无关的也抄。
- 断点：服务端把 JSON 字段拼成段落文本（`advisor.ts` 拼 summary / doubts / conflicts 那段）。
- 期望：
  - 回复是模型自己写的话，可以用 Markdown，页面已经按 Markdown 排了，列表、表格都能显示；
  - 检查结果只说这次提议新带出来的冲突；
  - 提议仍然走待确认，卡片里有结构化明细，对话里不用重复一遍。

**3. 自然语言加的规则，检查管不住。**
- 现象：在顾问里说「苏州城宵禁，入夜城门关闭」，接受以后规则里有这一条；但有人半夜出阊门，检查不报。
- 断点：
  - `advisor.ts:173` 交上来的规则一律是 `machine: null`；
  - `check.ts` 约 492 行，没有 `machine` 的规则只进「未覆盖」：「这条规则还是自然语言，程序判不了」；
  - 程序能判的只有 `teleport / remote_presence / resurrection / custom` 四类，顾问从来不往这里翻。
- 期望：
  - 顾问能把规则翻成程序能判的形式，就翻过去，并在提议里用人话写清楚「翻成了什么、管哪些事」，作者确认时看得懂；
  - 翻不了的规则，比如宵禁这种和时段、地点相关的，检查时由模型读相关事件来判，判出来的标黄色「疑似」，附上原句和理由，不算确定冲突；
  - 这一步的花费照常记，失败给原因，不伪造「通过」；
  - 「未覆盖」只留连模型都判不了的规则，并写明为什么判不了。

## 这个模式要有的

- **共享上下文**（自动带进会话，不用作者贴）：
  - 当前世界观：在作品里打开时，是这部作品的实际设定（`effective`）；
  - 当前作品、章、场，和作者正在看的那条设定或事件；
  - 最近的检查结果。
- **工具**：
  - 读：世界观快照、事件、轨迹、检查、作品正文、版本差异；
  - 写：只能交提议，作者接受才入账；
  - DSH 本来就有的通用工具照常开：搜索、抓取、bash/读文件，用户说过「完全开放」。
- **角色差别只在工具和提示词底线**：
  - 设定顾问：交设定类提议；
  - 写作助手：交正文改稿（`text_edit`）。
  - 提示词只写底线，不教模型怎么做。

## 不变的

- 契约 20 里提议的种类、`text.accept`、`Proposal.resolution`、`sync.suggest` 的语义都不改；要改先回来说。
- 费用只记不拦；key 只在进程内存里读。
- 页面这边：`CreativeAssistant` 现在每句都新建运行。DSH 给出「续一句」的接口（比如 `POST /v1/kernel/runs/:id/messages`，或者沿用研究台已有的方式），我这边改成续在同一会话里。

## 交付单写清楚

- 续一句走哪个接口；会话什么时候算结束、怎么新开；
- 每轮的上下文里自动带了哪些东西；
- 两个角色各开了哪些工具；
- 跑一次多轮对话（三轮以上，后一轮引用前一轮）大概花多少；
- 规则：哪些说法能翻成程序可判的形式；模型判规则在什么时候跑（每次检查，还是只在规则或相关事件变了时），一次大概花多少。
