# ReinLab 设计纲领（用户手写，2026-10-27 起生效，优先级最高）

## 原则

0. **核心：功能！功能！功能！** 不要搞一堆边缘 case。
1. **前端最终效果已定、最终要求已定**，所有工作朝这个方向推进。
2. **CC（Claude）负责验收**：按已定的前端效果来验收。
3. **Codex 负责设计，不写代码。**
4. **后端代码的实现、审核、测试都由 DS V4.1（DSH）完成。前端仍由 CC 写**（用户 2026-10-27 澄清）。
5. **CC 负责规划下一阶段**：做什么、怎么验。
6. **Codex 负责模块设计**：澄清设计，产出 PRD。
7. **DSH 负责具体实施**；遇到问题要好好问。
8. **DSH 的工作流**：To spec → To TDD → …（参照 Matt Pocock 的工作流）。

## 流程（每个功能一轮，一轮一个分支）

```
用户 ─①→ CC ─②→ Codex ─③→ (与用户 grill) ─④→ DSH ⟲
  ↑                                           │
  ├────────────⑤ 实施中的问题 ←───────────────┤
  │            CC ←──────⑥ 完成，开始验收 ────┘
  └←⑦ 反馈 + 判断是设计问题还是实现问题
⑧ CC、Codex、用户都没有问题 → 合并分支
⑨ 用户开启下一个分支
```

| 步 | 谁 | 做什么 |
|---|---|---|
| ① | 用户 ↔ CC | 确认下一个功能和验收标准 |
| ② | CC ↔ Codex ↔ 用户 | 确认下一段实现和方案 |
| ③ | Codex ↔ 用户 | grill 后完成 PRD |
| ④ | Codex → DSH | 把 PRD 交给 DSH，DSH 开始工作流（spec → TDD → 实现 → 自审 → 测试） |
| ⑤ | DSH ↔ 用户 | 实施中的问题和用户确认 |
| ⑥ | DSH → CC | 完成后通知 CC，开始验收 |
| ⑦ | CC → 用户 | 反馈结果，并判断是**设计问题**（回 Codex）还是**实现问题**（回 DSH） |
| ⑧ | CC + Codex + 用户 | 都没有问题后合并分支 |
| ⑨ | 用户 | 开启下一个分支 |

## 各方产出

- **CC**：前端代码；每个功能的「功能 + 验收标准」（步骤 ①）；验收结果，即真实走查的短片、给 AI 的 RESULTS、给用户的 REPORT（步骤 ⑦）。
- **Codex**：PRD，放在 `design/backend/` 或 `design/prd/`（步骤 ③）。
- **DSH**：后端的 spec、测试、实现，每批一个提交，每个功能一个分支（步骤 ④⑤）。
