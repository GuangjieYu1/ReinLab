## 一、工程开发台 ENGR

### 1. 模型

```
档案 (File) = 一个工作区 = 一个 Git 仓库
  ├ 需求面   requirements/   需求文档，像代码一样管理
  ├ 开发面   issue = 分支 = 会话，三者一一对应
  ├ 测试面   cases/          用例由需求的验收标准生成
  └ 本体面   ontology/       需求树 / 本体模型，develop 为准
```

**一条需求的生命周期**

```
在需求分支上修改 ──▶ WhatIf 检查（对照本体模型）
                       ├ 有逻辑问题或本体冲突 ──▶ 生成 md 报告 ──▶ 修改后重新检查
                       └ 无冲突 ──▶ 提交 MR ──▶ 人工审核 ──▶ 拆成 issue（进入开发面）
issue ──▶ 自动建分支 feat/ISS-<号>-<短名> + 新会话 ──▶ 开发 ──▶ 标记「待测试」
待测试 ──▶ 测试面按需求生成用例 ──▶ 运行 ──▶ 全部通过 ──▶ 合并 develop ──▶ 本体面更新
```

**生产力的核心：追溯链。** 任何一个对象都能一键看到它的上下游：
`需求条目 REQ ⇄ 验收标准 AC ⇄ issue ⇄ 提交 ⇄ 用例 ⇄ 本体概念`。
这条链在四个面里都是同一个侧栏组件（「追溯」页签）。

### 2. 全局框架

- 顶栏下方是**面签**：`需求 2 · 开发 5 · 测试 3 · 本体`，数字是该面待你处理的数量（橙色）。
- 面签右侧：**分支选择器**（全局）+ `⌘K`。
- 状态条：`develop @ a1f3c9 · 需求待审 1 · issue 5 · 待测 2 · 冲突 1 · 示例数据`。
- Agent 坞在四个面都在最右侧，但**维护对象随面切换**：需求面是当前需求变更集，开发面是当前 issue，测试面是当前测试批次，本体面是当前分支。

### 3. 需求面 · 文档 IDE

主视觉是一个**需求文档编辑器**，需求就是带结构的 Markdown，受 Git 管理。

```
┌ 01 需求目录 ─┐┌ 02 需求文档 ─────────────────────┐┌ 03 WhatIf ───┐┌ 04 需求助手 ┐
│ 树形大纲     ││ REQ-012 档案浏览器 · 键盘与窄屏  ││ 检查结果     ││ 计划         │
│  REQ-010     ││ ─────────────────────────────── ││  冲突 1      ││ 建议：       │
│  REQ-012 M●  ││ 用户故事                         ││  逻辑 1      ││ 补验收标准   │
│  REQ-013 A   ││ 验收标准 AC-1 Given/When/Then    ││  通过 6      ││ 解释冲突     │
│              ││ 约束                             ││ 每条可跳回   ││ 按报告修改   │
│ 变更集       ││ 术语带下划线 = 本体概念          ││ 文档与本体   ││ 提交 MR      │
│  2 个文件    ││ 左侧边栏显示与 develop 的 diff   ││              ││ 对话…        │
└──────────────┘└──────────────────────────────────┘└──────────────┘└──────────────┘
```

**01 需求目录**
- 树形大纲：领域 → 需求条目。`M` 已修改、`A` 新增、`●` 未检查。
- 下方「变更集」：像 git 暂存区，列出本次要提交的需求文件。

**02 需求文档**（衬线正文，行宽 68 字符）
- 结构化块：用户故事、验收标准（Given / When / Then，每条有 `AC-n` 编号）、约束、非功能要求、开放问题。
- **术语即本体**：文中出现的本体概念自动加下划线，悬停显示定义、关系和被哪些需求引用；不在本体里的新术语显示虚线下划线，提示「是否加入本体」。
- 左侧槽：与 develop 的行级 diff。
- 右上：`检查 WhatIf` 按钮。

**03 WhatIf 报告**
- 点「检查」后，把本次变更假设合入本体，运行检查，生成一份 md 报告（ReportDoc 构件）。
- 问题分两类，颜色不同：
  - **逻辑问题**（需求自身矛盾、验收标准不可测、条件不完整）——警示色
  - **本体冲突**（与已有概念、约束、关系冲突）——危险色
- 每条问题：严重度 · 一句话说明 · 涉及的需求行（点击跳转，光圈对焦）· 涉及的本体节点（点击跳本体面）· 建议修改。
- 顶部是闸门：`冲突 1 · 逻辑 1 → 不能提交 MR`。全部清零后变为 `可以提交`。
- 「提交 MR」按钮一直可点；有问题时点击会直接把视线带到第一条问题，而不是变灰。

**04 需求助手**
- 建议动作：`补验收标准` `解释这条冲突` `按报告修改` `拆分需求` `提交 MR`。
- 按报告修改时，助手的改动以 diff 形式出现在 02，逐段接受。
- MR 审核通过后，助手给出**拆 issue 预览**：按验收标准拆成若干 issue，你确认后进入开发面。

**动作表（节选）**

| 动作 | 风险 |
|---|---|
| `req_check_whatif` 运行 WhatIf | read |
| `req_apply_fix` 按报告修改 | write |
| `req_submit_mr` 提交 MR | write |
| `req_approve_mr` 通过 MR | danger（只能人点） |
| `req_split_issues` 拆分为 issue | write |

**实现状态（2026-10-16，第二版，按用户的思路重做）**：`src/components/workbenches/engineering/`，全部本地模拟。
- 左：需求文档目录，单击选中、双击打开；可收起成一条细边；每份文档有「写完」进度条。
- 中：文档编辑区，可单列或两列并排对照（双击打开到当前聚焦的列；助手的「跳到原文」在并排时打开到右列）。
  - 实时补全：停顿 280ms、光标在段末时给出灰色补全，Tab 接受、Esc 放弃、Enter 新起一段；中文输入法组字时不打扰。
  - 写完整的段落（验收标准 Given / When / Then 齐全并以句号结尾）字色变为深绿；左侧方块：绿 = 写完，空 = 编写中，橙 = 有标注。
  - 本体术语自动加下划线，悬停看定义、关系与约束。
- 校验：把与 develop 相比的 diff 通过 MCP（`ontology-checker / check_consistency`，配置在工具条的 MCP 面板）交给本体论模型；
  返回的意见以标注钉在原文上（原文片段波浪线 + 旁边的标注卡），每条附修改选项，点选即自动修正；
  不认同时在标注里写下理由「短提交」，模型接受后记入分支会话（每个分支一个 session），下一轮校验不再提出。
- 原来中间偏右的 WhatIf 栏取消。
- 右：需求助手。问「帮我找到某功能的全流程」会回复一张交互卡片（步骤 · 文档 · 原文摘录），点任一步跳到原文。

### 4. 开发面

```
┌ 01 待办 ─────┐┌ 02 预览 · 接口 · Diff · 终端 ────────┐┌ 04 开发助手 ─┐
│ ↻ 刷新       ││ 页签切换；预览带宽度标尺与元素点选   ││ ISS-34       │
│ ISS-34 进行中││ 接口：端点列表 · 请求 · 响应 · 历史  ││ 计划 4/6     │
│ ISS-35 待开始││                                      ││ 建议：       │
│ ISS-31 待测试│└──────────────────────────────────────┘│ ToSpec       │
│ ───────────  │┌ 03 Archify ─────────────────────────┐│ ToTDD        │
│ 资源管理器   ││ 结构图，本 issue 波及模块高亮        ││ 标记待测试   │
│ 文件/库/服务 ││                                      ││ 对话…        │
└──────────────┘└──────────────────────────────────────┘└──────────────┘
 状态条：feat/ISS-34-keyboard-nav · 检查点时间轴 · 测试 3/4
```

**01 待办**
- 顶部 `↻ 刷新`：拉取需求面审核通过后生成的 issue。
- 每条 issue：编号 · 标题 · 来源需求（REQ-012 · AC-2）· 状态（待开始 / 进行中 / 待测试 / 已合并）· 分支名。
- **点一条 issue 就切换整个开发面**：分支、会话、预览、Archify 高亮全部切到这个 issue。
- 新 issue 第一次打开时自动建分支，命名 `feat/ISS-<号>-<短名>`（修复类为 `fix/`）。
- 下半部分：资源管理器，页签「文件 / 数据库 / 服务」。AI 改过的文件带橙点。

**02 预览 · 接口 · Diff · 终端**（同一块区域四个页签）
- **预览**：前端实时预览，宽度标尺（含断点刻度）、元素点选（引用到对话）、改动区域标注。
- **接口**：从 OpenAPI 读出端点列表；选中端点 → 编辑请求 → 发送 → 看响应与耗时；每次请求存入历史。开发完成后点「刷新接口」重新读取端点，**新增和变更的端点标橙点**。
- **Diff**：本分支相对 develop 的改动，支持行内评论，评论直接发给开发助手。
- **终端**：dev server、测试、构建的输出。

**03 Archify**
- 项目结构图。本 issue 波及的模块高亮；点模块 → 资源管理器定位文件、对话中相关记录光圈对焦。

**04 开发助手**
- 维护对象：当前 issue。**一个 issue 一个会话**，切 issue 即切会话。
- 建议动作随阶段变化：
  - 刚开始：`ToSpec`（从需求生成技术规格）、`ToTDD`（先写失败的测试）
  - 进行中：`ToImpl`、`跑测试`、`刷新接口`
  - 测试全绿：`ToReview`（自查 diff）、`标记待测试`
- TDD 循环进行时，计划区显示莫比乌斯（红 → 绿 → 重构）。

**实现状态（2026-10-16）**：开发面已做成可交互的前端（`engineering/DevFace.tsx`），全部本地模拟。
- 布局与需求面一致、贴边：左 IDE 式资源管理器（活动栏：文件 / 搜索 / 源代码管理 / 追溯；分节：待办 issue · 代码仓库 · 数据库 · 服务）｜中 控制条 + 预览 · 接口 · Diff · 终端（+ 双击文件开代码页签）+ Archify + 检查点时间轴｜右 开发助手。
- issue = 分支 = 会话：点 issue 切换整个开发面；首次打开自动建分支、开新会话。「↻ 刷新」从需求面拉取新 issue。
- 动作表：ToSpec / ToTDD / ToImpl（写入，审批）· 运行测试 / 刷新接口 / ToReview（只读）· 标记待测试（写入），按钮与助手共用；TDD 进行时显示莫比乌斯。
- 预览：390 / 768 / 1280 宽度与标尺、点选元素引用到对话、本 issue 改动区域的橙色虚线框与标注；接口：端点 → 请求 → 响应 / 历史，刷新后新增与变更的端点标橙点；Diff：点任意一行写评论，发给开发助手。

### 5. 测试面

```
┌ 01 测试队列 ─┐┌ 02 用例详情 ──────────────────────────┐┌ 04 测试助手 ┐
│ 待测试 issue ││ CASE-118 窄屏下列表竖排               ││ 批次 #7      │
│ ───────────  ││ 来源 REQ-012 · AC-3                   ││ 建议：       │
│ REQ-012      ││ 步骤 · 期望 · 实际（失败行锈色）      ││ 批量跑键盘类 │
│  AC-1  ✓✓✓   ││ 失败定位：截图对比 / DOM / 接口 diff  ││ 为 AC-3 补   │
│  AC-3  ✓✗    ││ ┌ 录制回放（暗室）┐                   ││  边界用例    │
│ REQ-013      ││ │ 带步骤刻度       │                   ││ 分析报告     │
│  AC-1  ◌     ││ └──────────────────┘                   ││ 对话…        │
└──────────────┘└────────────────────────────────────────┘└──────────────┘
                ┌ 03 运行矩阵 · 报告 ────────────────────┐
                │ 用例 × 环境 状态格 · 覆盖率 · 生成报告  │
                └────────────────────────────────────────┘
```

**01 测试队列**
- 上：开发面标记为「待测试」的 issue。
- 下：用例树，按 需求 → 验收标准 → 用例 组织。每个用例一个状态格（通过 / 失败 / 不稳定 / 未运行）。

**02 用例详情**（点用例进入）
- 头部：用例名 · 来源需求和验收标准（可跳回需求面）· 最近运行时间。
- 步骤表：步骤 · 期望 · 实际，失败的步骤锈色底。
- **失败定位**（这是这个面的价值所在）：
  - 前端用例：期望截图 vs 实际截图并排 + 差异高亮；出错时的 DOM 片段
  - 接口用例：期望响应 vs 实际响应的 JSON diff
  - 堆栈与日志，定位到具体文件和行，可一键带到开发面
- **录制回放**：前端功能测试运行时，右下角弹出一个小窗实时录制；结束后在这里回放，时间轴上标出每一步和失败点。

**03 运行矩阵 · 报告**
- 用例 × 环境（桌面 / 平板 / 手机宽度）的状态矩阵。
- 「生成报告」：完整测试报告（ReportDoc）——摘要、按需求的覆盖率、每个失败的截图和录制片段、环境信息、与上次运行的对比。可导出 md / PDF。

**04 测试助手**
- 自然语言批量操作：「跑所有键盘相关的用例」「只重跑失败的」「在 390 宽下再跑一遍」。
- 用例生成：「为 AC-3 补边界用例」→ 生成用例草稿，审批后加入。
- 报告分析：「这次失败的共同原因是什么」。
- 批量运行时显示莫比乌斯。

**实现状态（2026-10-16）**：测试面已做成可交互的前端（`engineering/TestFace.tsx`）。接口测试从开发面移到这里：端点 · 请求 · 响应 · 断言，并对照 openapi.yaml 做契约检查。
- 左：测试队列 + 用例树（需求 → 验收标准 → 用例，每个用例三个环境的状态格）· 中：用例详情（步骤表、失败定位：截图对比 / DOM / JSON diff / 堆栈，「带到开发面」直接切到对应 issue）· 录制回放（暗室，时间轴标失败点）· 接口 · 矩阵与报告 · 右：测试助手（重跑失败、390 宽重跑、补边界用例、按契约生成接口用例、分析共同原因、生成报告）。

### 6. 本体面

```
┌ 01 分支 ─────┐┌ 02 需求树 / 本体图 ──────────────────┐┌ 03 节点 ─────┐┌ 04 本体助手 ┐
│ develop ●    ││ 默认显示 develop（无冲突）            ││ 概念：档案   ││ 「这个改动会 │
│ req/REQ-012 ▲││ 选其他分支时叠加 WhatIf：             ││ 定义 · 关系  ││  影响哪些需 │
│ feat/ISS-34  ││   新增 橙色 · 删除 删除线             ││ 追溯：       ││  求？」      │
│ 对比模式     ││   冲突 锈色虚线边                     ││ REQ ⇄ ISS ⇄  ││              │
│              ││ 树 ⇄ 图 切换                          ││ 提交 ⇄ 用例  ││              │
└──────────────┘└──────────────────────────────────────┘└──────────────┘└──────────────┘
```

- **01 分支**：develop 永远在最上，标「无冲突」。其他分支显示冲突数（▲）。可选两个分支进入对比模式（左右并排）。
- **02 需求树 / 本体图**：两种视图切换。
  - 树：领域 → 需求 → 验收标准，像目录
  - 图：概念与关系，像知识图谱
  - 选中非 develop 分支时，叠加该分支的 WhatIf 结果：新增节点橙色，删除节点删除线，冲突处锈色虚线边并带 ▲。
- **03 节点**：选中节点的定义、关系、约束，以及**追溯链**（被哪些需求、issue、提交、用例引用）。
- **04 本体助手**：影响分析（「改这个概念会影响哪些需求和用例」）、解释冲突、建议如何消解。

**实现状态（2026-10-16）**：本体面已做成可交互的前端（`engineering/OntoFace.tsx`）。
- 左：分支（develop 在最上，其他显示冲突数，可选一条「对比」并排）· 中：本体图（SVG，无 WebGL）⇄ 需求树，叠加 WhatIf：新增橙、修改墨虚线、删除划线、冲突锈色虚线 + ▲ · 节点详情：定义、约束、关系、冲突、追溯链 · 右：本体助手（影响分析会在图上框出波及的概念、解释冲突、建议消解）。

## 二、创作工作台 CRTV

### 1. 模型

```
档案 (File) = 一个创作项目
  ├ world/   世界观：人物、地点、势力、物件、规则、年表 —— 唯一事实来源
  ├ novel/   小说：卷 → 章 → 场景
  └ video/   视频：场景 → 镜头 → 白模 → 成片
```

**核心思路：世界观就是创作台的「本体」。** 与工程台的需求/本体同构——小说和视频都引用世界观里的实体（`@林墨`、`@旧港`），Agent 持续检查正文和镜头是否与世界观矛盾（比如第 3 章写她左撇子，设定里是右撇子）。工程台的 WhatIf 报告构件在这里复用为「设定冲突报告」。

**三个面之间的流向**

```
世界观 ──引用──▶ 小说 ──「转为分镜」──▶ 视频
   ▲                 │                     │
   └── 新设定回写 ───┴──── 设定冲突检查 ───┘
```

### 2. 世界观面

```
┌ 01 条目索引 ─┐┌ 02 世界 ──────────────────────────────┐┌ 03 条目 ─────┐┌ 04 设定顾问 ┐
│ 人物  12     ││ 视图：关系图 · 年表 · 地图             ││ 林墨         ││ 建议：       │
│ 地点   8     ││                                        ││ 立绘 · 三视图││ 补全外貌     │
```

### 4. 视频面 · 白模分镜 → 成片

**流程**（参考 Seedance 2.5 的 3D blockout-to-video 工作流）

```
场景 → 镜头表 → 3D 白模（低精度建模 + 机位 + 人物占位）→ 渲染白模参考
     → 视频生成（白模参考 + 世界观人物三视图 → 成片）→ 配音 / 音乐 → 剪辑 → 导出
```

白模的作用：先用便宜的低精度三维场景**锁定构图、景深、人物站位和运镜**，再交给视频模型出成片。比直接文生视频可控得多，重做一个镜头也只花一次生成的钱。

```

┌ 01 镜头 ─────┐┌ 02 暗室查看器 ────────────────────────┐┌ 04 镜头检查器 · 导演助手 ┐
│ 场景3 旧港   ││ ┌──────────────────────────────────┐  ││ 镜头 12                  │
│  12 中景 ▣▶  ││ │  三维白模视口（可环绕、可调机位）│  ││ 景别 中景 · 运镜 推      │
│  13 特写 ▣   ││ │  人物占位绑定 @林墨              │  ││ 时长 4s · 动作描述       │
│  14 远景 ▢   ││ └──────────────────────────────────┘  ││ 参考：林墨三视图（自动） │
│ 场景4 …      ││ 视图：白模 · 成片 · 叠加对比          ││ 候选 v1 v2 v3 v4         │

└──────────────┘└────────────────────────────────────────┘└──────────────────────────┘
┌ 03 时间轴：画面 · 对白 · 音乐 三轨 + 底部一镜一格快照导航 ─────────────────────────┐
```

- **阶段条**：每个阶段完成了多少镜头、生成队列、累计费用。队列运行时显示莫比乌斯。
- **01 镜头**：按场景分组；每个镜头的缩略图可在白模和成片之间切换；状态图标：`▢` 未建模、`▣` 已建模、`▶` 已出成片。
- **02 暗室查看器**（暗色）：
  - **白模**：三维视口，环绕查看、拖动机位、编辑机位路径；人物占位与世界观实体绑定。
  - **成片**：播放生成结果。
  - **叠加对比**：成片半透明叠在白模上，检查构图是否被保留。
- **04 镜头检查器 · 导演助手**：镜头参数、自动附带的参考（世界观人物三视图）、候选版本（v1–v4，助手可先预选）、生成按钮带价格（`write` 风险，需确认）。
- **03 时间轴**：画面、对白、音乐三轨，底部一镜一格快照导航，与镜头列表、查看器同步。

**动作表（节选）**

**白模视口：不用 WebGL，用 Canvas 2D 软渲染。**
> 2026-10-23 更新：后端改为暂用 Blender 无界面模式渲染视口画面和参考图。前端仍不用 WebGL；交互太慢时再议。见 [ARCHITECTURE_BENCHES.md 第 12 节第 9 条](ARCHITECTURE_BENCHES.md)。

**视频面（2026-10-17）**：`creative/VideoFace.tsx` + `Viewport.tsx`。参照 Intangible 的 Build → Compose → Visualize。

- Compose：导演助手按镜头表自动摆机位与运镜终点；编辑视角里机位、视锥、运镜路径可拖；机位视角带 16:9 安全框与三分线；三轨时间轴播放时沿运镜插值。
- Visualize：每镜 ¥2.4（模拟）生成成片，占位图 +「模拟生成」，候选 v1–v4，成片 / 叠加对比；连续性检查覆盖光线（黄昏 / 正午）。

## 四、研究工作台 RSCH

**三种模式（2026-10-17 与用户对齐）**，每份研究档案选一种，模式之间一键串联：
精读的洞见 / 疑问 →「派给群研」；群研里可量化的子任务 →「交给自研」；自研的结论回写为发现，链接回出发的论文。

### 1. 精读 · READ —— 目标是「搞懂」
- **解析**：一句话 → 直觉（比喻）→ 机理（逐步）→ 证据（实验证明了什么、没证明什么）→ 洞见与局限。每层都链接回原文段落，点哪句跳到哪句。
- **动画实验室**：可交互的解释动画（Canvas 2D / SVG，不用 WebGL），可拖参数、点元素，看机理如何变化。
- **复现**：有代码时跑一个最小复现，把结果与论文的结论对照；规模不够时明确写出「复现到了哪一层」。
- **理解检验**：AI 出题，你作答或用自己的话复述，它指出哪里理解偏了，并链接回对应的解析层。

### 2. 群研 · SWARM —— 目标是「攻下一个大问题」
- 弱化版 AI for math 思路：总负责人拆任务树（猜想 → 引理 → 子情形 / 调研 → 子问题），几十个子 agent 分头搜索、推导、找反例、验证。
- **通信是主角**：通信总线以动画流呈现每条消息（领取 · 提问 · 交付 · 求助 · 转交 · 反驳），可暂停、回放、点开；共享留言板，用户可以插话、给某个 agent 下指令。
- 汇总：结果层层合并，失败路径保留。

### 3. 自研 · AUTO —— 目标是「达到一个数字」
- 输入任意数据（PDF → OCR、图片文件夹 → 视觉任务、Excel → 表格预测）+ 目标 + 预算；系统识别数据类型、提出指标与算法候选。
- 打分需要标准答案：定题阶段请用户标注一小批样本（如 20 页），或确认替代的估计方式。
- 运行：参照 karpathy/autoresearch「改 → 跑 → 评 → 保留或回滚 → 记一行」，最优前沿曲线 + 目标线，达到即停；预算 50% / 80% 审批。

**实现状态（2026-10-17）**：三种模式均已做成前端（`research/`），全部为本地示例与模拟。
- 精读：示例论文《Attention Is All You Need》（内容为转述）；三个可交互动画（缩放点积 / 位置编码 / 多头）在本地真实计算。
- 群研：32 个 agent、8 种角色、7 种消息的示例剧本；状态只由时刻推出，时间轴可暂停、拖动、回放；留言板可 @agent 下指令（追加到剧本）。
- 自研：定题 / 运行 / 报告。
- 已知限制：切换模式时当前模式的状态不保留。

## 五、自动化工作台 AUTO

形态参照 Agent 例程（Claude Code routines / ChatGPT Tasks）：一条例程就是一段自然语言指令，Agent 每次照着自己执行；界面以指令和运行记录为主，不画流程图。

1. **编排 COMPOSE**：例程书——01 指令（@ 引用工具、# 引用档案；说不清的短语橙色虚线标出，点选一个说法替换）/ 02 触发（定时用一周 × 24 小时的格子显示）/ 03 工具与权限（允许 / 询问 / 禁止；危险动作不能设成允许）/ 04 产出与预算 / 05 版本。右栏「AI 的解读」把指令拆成它会执行的步骤，标出每步用的工具和会停下来问你的地方；「预演」逐步走一遍，不调用工具也不写入。一句话新建例程：助手起草指令、触发与权限（写入默认询问），并标出需要说清的地方。
2. **运行 RUNS**：所有例程近 14 天的运行矩阵（成功 / 有提醒 / 失败 / 等你确认）+ 选中运行的逐步记录（思考 · 工具调用可展开输入输出 · 产出 · 审批 · 错误）。写入停在「等你确认」，就地批准或驳回；「立即运行」一步步长出来。侧栏有今天的时间表和跨例程的待确认收件箱。
**节点 GRAPH**（第二个面）：照 ComfyUI + ComfyUI-Workspace-Manager 的布局与交互，换莱茵生命的皮。左侧工作区：工作流（按文件夹、标签、版本、未保存圆点）/ 模型管理（缺失的模型标红并显示被哪个工作流引用，可安装）/ 画廊（这个工作流的历史输出，点开可载入种子）。中间：多开标签栏 + 节点画布（插槽和连线按类型着色；拖线到同类型输入，松在空白处弹出只列能接上的节点；双击搜索加节点；组框连同节点一起拖；滚轮缩放、小地图）。右上角浮动队列：排队运行（⌘↵）、批次、队列与历史缩略图。排队前校验（缺输入、缺模型 → 节点标红）；执行时节点逐个高亮，K 采样器按步数推进，参数和上游没变的节点直接用缓存，排队后按 control_after_generate 改种子。节点以生成式为主（Checkpoint / LoRA / CLIP 编码 / K 采样器 / VAE / ControlNet / 放大 / 保存），另有通用节点（读档案、Agent 写提示词、写入档案）；「写入档案」运行时停下来等你批准。一张图可以「发布为工具」：选要暴露的参数，例程在指令里写 @工具名 调用（WF-05 用 @cover_graph 生成封面，编排面的工具表里能直接打开对应节点图）。一句话也能搭图。生成结果为按种子确定的「模拟生成」占位图。

3. **维护 MAINTAIN**：维护 Agent 按 诊断（失败那一步 + 证据 + 原因 + 置信度）→ 修复（指令 / 配置的 diff）→ 沙盒重放（用失败那次的输入重跑，再回放最近几次成功运行做回归，外部写入全部拦截）→ 人审上线（只有你能批准；版本 +0.1，改动写回编排面的指令）。

**看板 LIVE**（第五个面，2026-10-20 新增，设计见 [AUTOMATION_LIVE.md](AUTOMATION_LIVE.md)）：常驻自动化 = 脚本 + 旋钮 + 声明式面板 + 维护 Agent。总览把所有常驻自动化排成实时小面板（一拍 = 1 分钟），告警只在状态翻转时通知一次、连续 5 拍正常才解除。点开一个：放大的面板（折线 / 统计 / 表格 / 柱状 / 盘口深度 / 模拟对照，全部 SVG）、清单 automation.yaml、日志；右栏旋钮按风险分流——低风险直接热更新并记版本，中 / 高风险走审批卡，可回到上一版。接入流水线把 GitHub 项目 / 研究台成果 / 一句话想法 / API 走成 侦查 → 适配（生成四件套）→ 沙盒试跑 6 拍 → 你批准上线。只观察和告警：交易类请求一律拒绝。示例：LV-01 新能源车舆情、LV-02 BTC 盘口波动（只看）、LV-03 舆情扩散模拟（OASIS）、LV-04 arXiv 新论文雷达（研究台委托）。

**实现状态（2026-10-18）**：`automation/`。三个面均已做成前端；8 条例程、4 个故障（INC-14 开局已走到「沙盒重放」，对应档案简报里的「修复 diff 已生成，等待沙盒试跑」）。解读、起草、诊断与重放全部为本地模拟。

## 六、探索工作台 EXPL

目标：生成一份能照着走的**拍照计划**——机位、时间、天气、给模特的引导词与出图提示词、服饰参考。人像外拍为主，兼顾风光；没有模特的机位自动隐藏引导词与服饰。

1. **计划 PLAN**：莱茵风格的简化矢量地图（京都东山：鸭川、疏水、白川、街道、东山等高线、寺社）；机位按时间连成步行路线；选中机位时叠加镜头视角扇形、日出 / 日落方位线、当前时刻的太阳方位与影子方向（参照 PhotoPills）。底部时间线：光线带（蓝调 / 金色时刻）+ 太阳高度曲线 + 逐时天气 + 机位时段 + 换装点，拖动播放头太阳跟着走。「生成拍照计划书」逐节写出：概要、时间表、机位（构图 / 引导词 / 出图提示词 / 规定 / 备选）、服饰（色板 + 搭配卡 + 模拟生成参考图）、天气预案、装备。
2. **机位 SPOT**：Canvas 2D 的 2.5D 白模（不用 WebGL），按当前时刻的太阳投影影子，被山挡住时没有直射光；「机位视角」按镜头焦距换算视角，人像竖拍 2:3、风光横拍 3:2，叠三分线。右栏：参数与光线、山影、人流、构图、给模特的引导词（配姿势简图，可复制）、出图提示词（生成样片 / 交给自动化台节点图）、服饰、规定与雨天备选。
3. **现场 FIELD**（按 iPad 横屏设计）：现在该拍哪个机位、倒计时、此刻的光、引导词、「拍到了」与一句话记录、小地图上的当前位置、今天的清单。「情况变了」（下雨 / 晚到 / 人多）由助手重排，先给前后对照，点「应用」才改计划。
4. **回顾 REVIEW**：照片按位置落回地图，时间线叠「实际」轨道对照计划；精选（按机位分组、星级、挑片）；现场碎片由助手按主题（光线 / 人流 / 服饰 / 天气 / 规定 / 机位）整理并写游记草稿；「下次」的经验可以写回计划；结果交给创作台（作品集）、研究台（观察笔记）、自动化台（WF-06 照片归位），都要你批准。

**实现状态（2026-10-18）**：`explore/`。太阳位置按京都经纬度真实计算（NOAA 简化公式，日出 06:14、日落 17:08）；天气、人流、照片与现场记录为示例数据；地图不是真实比例；样片与参考图为「模拟生成」占位图。四份档案中只做了第一份（东山 · 秋日人像），其余为草稿。

## 七、课程设计工作台 CURR

来源：OpenMAIC（课堂）× DeepTutor（备课链）。**自学**：你既是审批人，也是学生；AI 分成顾问、备课、独立审查、讲师、复核等角色，彼此隔离。调研交给研究台，侦查与适配交给自动化台；课程台只发起、审批、收结果。

1. **备课 PREPARE**：门禁流水线 咨询 → 调研 → 侦查与适配 → 蓝图 → 单元备课 → 独立审查 → 开课门禁，每段之间是一道门。
   - 「讨论修改」不等于「批准」；批准只放行下一段，不会自动往下做。
   - 咨询：多轮对话 + 回答卡 → 学习目标（成功标准、基础、约束）与 Preflight Plan，写在 `study_plan/`。
   - 调研：方法与路线（不找教材），负结果照样记录。
   - 侦查：逐个核实「你能打开 · AI 能读 · 价格 · 未知项 · 替代」，失效来源留尝试记录；上传文件只解决对应缺口。
   - 适配：转换结果回到页码 / 时间戳并抽样核验；可选项失败不升级，核心缺口单独标红。
   - 蓝图：4 模块 8 单元，首轮只创建 U1；越级创建由接口拒绝（409），不是隐藏按钮。「蓝图 ≠ 单元已创建 ≠ 可以开课」三道边界常驻页头。
   - 备课包：目标、先修、可溯源讲解、练习、rubric、误区、补救、未确定项。
   - 独立审查：故意放入的错误解题、缺出处、错 rubric 必须判不通过；每轮只修失败项，最多三轮，没有降低标准的出口。
   - 开课门禁：已创建 + 审查通过 + 核心材料齐全 + rubric 锁定。
   - 底部动作画布记录每个实际动作（谁、做了什么、费用），可导出审计，复建同一顺序与费用汇总。
2. **学习 LEARN**：左侧单元地图（未创建 / 审查未通过 / 可开课 / 学习中 / 已通过；期末单独一项）。
   - 单元内标签：课堂（OpenMAIC SlideCanvas 原生渲染 + AI 老师讲解）/ 精读（原文 + 批注，页码可回到原 PDF）/ 练习（作答后才给参考）/ 复习（不泄露考核答案）/ 考核 / 收尾。
   - 右侧学习工作区：每个单元一条会话，提问自动带上单元、资源与位置。
   - 学习门禁：未开课或前一单元未通过时，页面、工作区、接口都拒绝推进。
   - 考核按锁定的 rubric 评分；异议由独立角色按同一版 rubric 复核，保留原判与更正，错误参考答案不计为你的错误。
   - 通过后才能「正式收尾」，生成学习者侧写与能力掌握档案（每条可追溯）；用更强模型重新分析需批准范围与预算，并保留旧版本。

**实现状态（2026-10-18）**：`course/`。示例课「群论 · 对称与群」开局停在 U1 独立审查第 1 轮不通过、侦查报告有一个核心缺口；其余三门课为草稿。课堂幻灯片由本地数据生成，经 `@openmaic/renderer` 渲染；连接服务器的原生课程（NativeCourse）不变。页码、时间戳、费用为示例数据。
