每次拿 ReinLab 的功能和外面成熟的产品对比，结论都追加在这里，新的放在最上面。每条写清楚：比的是什么、题目是什么、怎么判的、谁赢在哪、发现了我们哪些问题、后续怎么办。

## 2026-11-10（夜）· 视频片段拆解：运镜、演员动作、表情到帧级

用户要「放入视频片段，拆解运镜、演员动作、演员表情，到毫秒级描述」。

- **Motion Previs Studio**（wassermanproductions，Apache-2.0，Electron + TypeScript，2026-07 发布，和 Blockout 同一作者）：参考视频 → 骨骼视频（OpenPose BODY_25）+ 深度 + **运镜数据**（光流 + RANSAC，抠掉人物只看背景，解出摇 / 俯仰 / 变焦 / 滚转）+ Blender 导入脚本；「演员动作」「整场」两种模式；带 MCP。结果能直接送进 Blockout 重排。**最对口**。
- **运镜（6 自由度 + 深度）**：MegaSaM（CVPR 2025，Apache-2.0，基于 DROID-SLAM，能处理有人在动的画面，要 GPU）；VGGT 系列（权重许可分商用 / 非商用版，待核）；NVIDIA ViPE（近似真实尺度，许可待核）。
- **身体动作**：MediaPipe Pose（33 个关键点，含 3D 世界坐标，浏览器里能跑，逐帧带毫秒时间戳）；GVHMR / WHAM（3D 人体，SMPL 体系，非商用为主）。
- **表情**：MediaPipe Face Landmarker——每帧 478 个面部点 + **52 个表情系数**（眨眼、挑眉、嘴角、眼神方向…，ARKit 同一套）+ 头部姿态矩阵；Holistic 一次出身体 + 手 + 脸（553 点）。框架是 Apache-2.0，模型文件条款待核。
- **语义层**：看视频的大模型（方舟上的豆包视觉模型，同一个 key，视频理解支持 file_id）读关键帧 + 上面的数值曲线，写成带时间码的人话。

**精度说明**：「毫秒级」实际是**逐帧**——24fps 一帧约 42 毫秒，60fps 约 17 毫秒；时间码精确到毫秒，变化的分辨率受帧率限制。

**方法（我们的拆解管线）**：
1. 切镜（PySceneDetect / TransNetV2）；
2. 运镜：光流解摇 / 俯仰 / 变焦 / 滚转（照 Motion Previs Studio），要 6 自由度再上 MegaSaM；
3. 动作：MediaPipe Pose 逐帧关键点；
4. 表情：MediaPipe 52 表情系数逐帧；
5. 事件：从曲线里自动切出「开始转头 01.240」「眨眼 02.130–02.210」「嘴角上扬 03.000–03.500」；
6. 描述：视觉大模型把事件和关键帧写成镜头拆解表（时间码 + 运镜 + 每个人的动作 + 表情）；
7. 用途：驱动我们的人偶（动作重定向）、写进 Seedance 提示词（带时间码）、或者整段当参考视频「换人不换动作」。

## 2026-11-10（夜）· 生成白模：有没有成熟的开源项目

| 项目 | 做什么 | 许可 | 能不能直接用 |
|---|---|---|---|
| **Blockout**（wassermanproductions） | AI 视频预演：50+ 套灰盒环境（街道、超市、电影院、车厢、后院…）+ 人物 / 家具 / 道具库，**全部用代码程序化生成**、真实比例；按标记走位、194 种动作、39 种运镜；导出参考视频 + 深度 + 静帧 + 俯视走位图 + 提示词；带 MCP 让 agent 来摆 | Apache-2.0，TypeScript | **最对口**。可以借「环境套件 + 程序化道具库 + 标记走位 + 导出包」的做法，代码可移植（动作数据许可待核） |
| **CozyClay**（NomaDamas / HaD0Yun） | 浏览器里的预演：搭景、摆人、运镜和剪辑，agent 写「动作规格」由浏览器里的确定性编译器逐帧烘焙；有 Seedance 运镜控制、灰盒转视频的流程 | **AGPL** | 能学做法；代码不能直接并进我们的产品（AGPL 传染） |
| **ProcTHOR**（AllenAI） | 程序化生成整栋房子：平面（树图切分）→ 房间 → 摆家具；1633 件可交互物件 / 108 类、3278 种材质；房子是 JSON | Apache-2.0（代码、数据集、资产库） | 布局算法和 JSON 结构可参考；渲染靠 Unity / AI2-THOR，物件是现代西式家居 |
| **Holodeck / Holodeck 2.0**（AllenAI） | 一句话生成房间：模型写物件关系，约束求解器算坐标；资产从 Objaverse 检索 | 代码许可待核；资产许可混杂 | §13.8 已照它的思路改（关系 + 求解器） |
| **Infinigen Indoors**（Princeton） | Blender 里全程序化生成室内，家具也是程序生成 | BSD | 太重、现代西式为主 |
| **blender-mcp** | 让模型直接操作 Blender | MIT | 坐标仍靠模型算，不解决出界 |

**结论**：没有一个能直接生成「清代苏州客栈」的白模——它们的环境和家具都是现代西式。最值得借的是 Blockout 的整套做法：
1. **环境套件**：常见场景（客栈门厅、茶馆、街巷、城门、渡口、书房…）各做一套程序化的房间壳 + 默认陈设，导演先挑套件再改；
2. **程序化道具库**：八仙桌、长凳、柜台、货架、茶炉、条案、屏风、灯笼…每件用代码按参数生成（长宽高、样式），比方块像、比真模型便宜，天然能复用（就是用户说的「物件库」）；
3. **布局**：§13.8 的关系 + 求解器；
4. **走位和运镜**：标记 + 动作库 + 运镜库；
5. **导出包**：参考视频 + 深度 + 首末帧 + 俯视走位图 + 提示词（3B 用）。

## 2026-11-10（夜）· 对话创建架空世界地图 / 用已有虚拟地图：开源现状

起因：用户在顾问里说「使用中土世界地图作为底图」，顾问没有设底图的工具，只交了几条规则。用户要的是「对话创建架空世界地图、或沿用已存在的虚拟地图」。

- **没有现成的「一句话 → 二维幻想地图」开源工具**。通行做法是：大模型把描述翻成参数，交给程序化地图生成器，再用工具逐步改。
- **Azgaar Fantasy Map Generator**（MIT，浏览器，2 万多星）：最成熟的幻想地图生成器（地形、气候、国家、文化、城市、道路、河流），能导出 GeoJSON / JSON / SVG / PNG；我们 1A 已经支持导入它的道路 GeoJSON。没有官方 API，但已有两个 MCP：**mcp-for-Azgaar**（设生成参数、图层、定位、导出，能让 Claude 等模型驱动）和 fmg-mcp（Playwright 驱动）；应用里还有一个「Azgaar Assistant」（用户自带模型 key）。
- 其他：Worldsmith（MIT，浏览器，分形地形，导出 JSON / 高度图）、khalidibnwalid/map-generator（国家、城市、商路 + 历史模拟，确定性存档）、rhedak/fantasy-map-generator（Python，结构化配置出 SVG，适合模型写配置）、Confluent-AI（模型用函数调用改地形参数，三维高度场）。
- **已有虚拟地图**：中土有社区 GIS 数据——ME-GIS（第三纪元，shapefile：海岸线、河流、道路、城市、地名、等高线；现由 andrewheiss 维护）、Arda-Maps（三个纪元，含贝烈瑞安德、努门诺尔）、bburns/Arda（高程 DEM + 地名）。都要自己转 GeoJSON；**版权属托尔金遗产，自用参考可以，对外发布作品需另谈**。
- **结论**：我们的路线是「顾问 → Azgaar（经 MCP 或直接写配置）生成架空地图 → 导入为底图 + 路网」，以及「导入已有虚拟地图的 GIS 数据（ME-GIS 这类）为底图 + 地名 + 道路」。底图需要加一种「架空地图」类型：坐标系是平面（非经纬度），带比例尺，路网可以从地图数据里来。

## 2026-11-10（夜）· 动作和机位怎么控制：业界预演做法 + Seedance 小实验

**业界成熟做法（2026）**：先在灰盒 / 泥塑三维场景里把**走位和机位**定下来，渲染成一段参考视频，交给视频模型「照着拍」，人物长相用参考图。
- **Blockout**（开源，Apache-2.0，TypeScript，约 190 星，2026-08 仍在更新）几乎就是我们的视频面：真实比例的灰盒人偶和场景（代码生成）、按「走位标记」编排演员和机位、194 种人物动作 + 33 种运动路径、39 种经典运镜；导出包含参考视频 mp4（确定性渲染）、深度图、每个机位的静帧和**俯视走位图**、按目标模型（Seedance 2.0 / Veo / Kling / LTX / Wan）写好的提示词；还带 MCP，能让 agent 来摆。同作者的 Motion Previs Studio 能把参考视频拆成姿态、深度、机位。
- CozyClay（开源，浏览器里的预演）、Krea Seedance Studio（agent 从文字 / 参考图 / 草图搭简单三维场景）、即梦的 Blender 泥塑渲染插件、Intangible 都是同一路线。Seedance 2.5 自带「三维白模预演」。
- 「自己拍一段手机视频当动作参考」也是常用的低成本做法。即梦教程的口诀：「换人不换动作」——参考 @视频1 的运镜和动作节奏，把 @图片1 的人物换进去。
- 动作来源：**文字生成动作** HY-Motion 1.0（腾讯，许可受限：不含欧盟英国韩国、有月活上限）、MoMask（代码 MIT，但依赖 SMPL 和数据集，非商用）；**视频提取动作** GVHMR / WHAM（SMPL 体系，研究用为主），MediaPipe 姿态（Apache，浏览器里能跑，只到 2D / 粗 3D）。**人物替换** Wan2.2-Animate / Wan-Animate-2（阿里，Apache-2.0，14B，要大显存 GPU）。
- 结论：别自己从零造动作系统；人偶 + 动作库这块，Blockout 的做法（Apache-2.0、TypeScript）可以直接借鉴甚至移植。

**Seedance 小实验**（`design/walkthroughs/creative-3/scene-first/`）：
1. 第 2 镜的白模预演（mp4 24fps）+ 沈砚立绘，参考视频用 base64 传 → **400：reference_video 必须是公网 URL**。官方建议放火山 TOS 对象存储、设公共读；方舟 Files API 的 file_id 文档只写了用于视频理解。**要走参考视频，必须先开 TOS（或别的公网存储）。**
2. 退路：预演首帧当参考图 + 沈砚立绘 + 提示词，`doubao-seedance-2-0-260128` 480p 5 秒，227 秒出片，50638 token ≈ **¥2.33**（¥46 / 百万 token）。
   - **人物一致性很好**：沈砚和立绘是同一个人（灰绿直裰、玉佩、发髻、手持河道图卷）；顾嬷嬷是年长妇人、蓝灰衣；左右顺序对。
   - **场景和光线好**：门厅、窗棂、柜台油灯、门外雨。
   - **机位和站位基本没跟**：预演是低机位远景、两人在画面中间偏左、柜台在右；成片是平视中近景、柜台在左下、顾嬷嬷在柜台后。只给静帧，Seedance 只当松散参考。
3. **补测（TOS 开好后）**：预演 mp4 用 TOS 的 S3 兼容接口 + SigV4 预签名上传，签一个 2 小时的下载链接当 `reference_video`，**链路通了**。480p 5 秒，181 秒出片，100858 token（含参考视频）≈ **¥2.82**（¥28 / 百万）。人物仍一致；顾嬷嬷扶门框、沈砚回头这些动作按文字演出来了；**机位固定这点跟了，构图和站位没有 1:1**（预演里两人挤在左中、低机位、头顶一块悬空顶棚，成片是平视全身、一左一右）。对比图 `vid-compare.jpg`。判断：这段预演本身含糊（人偶不动、顶棚悬空、机位贴地），模型只取了大意。要测「到底能跟多紧」，得先做一段清楚的预演：房间正确、人偶会走、机位会推。
4. **把预演做清楚后再测**：人偶加四肢和动作（走位终点：前 70% 迈腿摆臂走过去，停下转向朝向；带鼻尖看得出朝向），客栈白模摆正（墙落地贴轮廓、顶棚在层高、柜台货架桌子真实尺寸），大面切块修掉画家算法遮挡，机位改成门边右角缓推。沈砚从镜头这侧走到柜台前转身，顾嬷嬷在柜台后。送 Seedance：247 秒，90814 token ≈ **¥2.54**。**构图、机位推进、家具位置、走位几乎 1:1 跟上**（柜台中左、货架在后、右前圆桌、沈砚从左入画走到柜台前停下转身），人物仍是立绘里的沈砚。对比图 `v2-compare.jpg`，预演 `shot2-clear-preview.mp4`，成片 `seedance-vid2.mp4`。
5. **场景模板 + 明清家具库再测**：门厅套「客栈门厅」模板（24 件：柜台、货架、油灯、酒坛、八仙桌 ×2、长凳 ×4、条案、匾额、茶炉、碗架、门窗），沈砚从左侧走到柜台前、顾嬷嬷在柜台后、缓推。154 秒，100858 token ≈ **¥2.82**。**布局几乎一一对应**（柜台在后方正中、货架坛罐在后、左前八仙桌长凳、左墙匾额条案），走位和推镜也跟上，青砖地木梁油灯气氛对。**一处自作主张**：在左后墙添了一道开着的门、门外下雨——预演里门在镜头背后的南墙，画面里看不见，模型就自己补了一个。对策：提示词写明「门在镜头背后，画面里的墙上没有门」，或者让预演里看得见门。对比图 `kit/v3-compare.jpg`。
6. 结论：**长相靠参考图已经够稳；机位、走位、动作要靠参考视频，而且预演越清楚跟得越紧**；场景模板 + 家具库让「家具是什么、在哪」也被跟住了（业界也是这么做的）。所以 3B 的前提是公网存储；预演本身也要做得「清楚无歧义」：人偶要有四肢和动作、比例真实、白模不能悬空乱飞。

## 2026-11-10（晚）· 「先出场景图再搭白模」+ 物件库：用户的两个思路

**思路一：先生成二维场景图，再按图搭白模。** 外面有成熟做法：Architect（NeurIPS 2024）明确说图像生成模型比语言模型更懂物件怎么摆，先画图再抠物件、估深度抬成三维布局；Imaginarium、Scenethesis（2025）是「看图出布局」；Diorama（ICCV 2025，开源）从一张图做架构重建 + 物件检索 + 布局优化。

**小实验**（Seedream 5.0 pro，门厅 10×8、层高 3.2 的文字描述，3 张 ¥0.9，各约 55 秒；图在 `design/walkthroughs/creative-3/scene-first/`）：

| 图 | 摆法（拓扑） | 尺寸 | 能不能用 |
|---|---|---|---|
| 平面图 `plan.jpg` | **对**：门在北墙正中、茶炉西北角、碗架挨着、柜台靠东墙北段、货架靠东墙南段、两张方桌居中偏南各配长凳、西墙开窗 | **不准**：画成斜俯视，外框比例 1.46（应 1.25），比例尺和「10 米」标注互相对不上 | 拿来读「放什么、在哪一片、挨着谁」很好；不能量尺寸 |
| 三视图拼图 `sheet.jpg` | 俯视那格对 | 三格互相矛盾：正立面（从南往北看）把门画在前面，侧立面把茶炉、桌、柜台排成一排 | **不能用**：场景三视图不像人物三视图，图像模型保不住三格一致 |
| 透视概念图 `persp.jpg` | 和平面图一致（西边茶炉碗架、东边柜台货架、北门外雨巷） | 无尺寸 | 好看，适合当成片的**画风和场景参考图**（3B 送 Seedance） |

**结论**：图适合定「放什么、大概在哪、长什么样」，不适合定尺寸。所以把图接在求解器前面，不是替代求解器：
1. 出一张平面图（加一张透视概念图）给作者看，作者满意再往下；
2. 看图模型从平面图读出物件清单和关系（「茶炉在西北角」「碗架在茶炉东边靠北墙」「柜台靠东墙北段」……），这正是 §13.8 求解器要的输入；
3. 求解器按真实轮廓和尺寸算坐标；
4. 透视图存成场景资产，镜头出片时当参考图。
需要一个能看图的模型（方舟上的豆包视觉模型同一个 key 可用，待 DSH 核实）。

**思路二：家具建好入库复用。** 外面的做法也是这样：Holodeck 从 Objaverse 检索、Digital Cousins 从 BEHAVIOR-1K 检索、Diorama 做形状检索。我们的版本：
- 「物件库」按账户共享，跨世界观复用；每件有稳定 ID、名称、类别（桌 / 凳 / 柜 / 架 / 炉）、真实尺寸、风格标签（明清 / 苏式）、版本、来源；
- 来源三种：白模方块（现在）→ 出一张物件参考图（Seedream，¥0.3）→ 图生 3D 模型（TRELLIS.2，MIT 许可；Hunyuan3D 2.1 许可受限不选）；
- 求解器摆件时先按类别 + 尺寸在库里找，找到就挂 `assetId`，没有才新建；白模部件引用 `(assetId, version)`，和人物形象同一套。
- 公开库（Objaverse 许可混杂、明清家具少）不作为主要来源。

## 2026-11-10 · 白模怎么搭：我们的「模型心算坐标」vs 开源的场景布局工具

起因：3A 两轮验收，导演交的白模一直出界、超高、悬空。根子是让语言模型直接写每个部件的三维坐标，连墙和顶棚也让它算。用户判断：「根据场景生成建模应该有专门的开源工具」。

| 工具 | 做什么 | 许可 | 和我们的关系 |
|---|---|---|---|
| Holodeck（AllenAI，CVPR 2024）/ Holodeck 2.0 | 一句话生成可交互房间：先出平面和墙、门窗，再选物件，**模型只写物件之间的关系**（靠墙 / 居中、靠近 / 远离、在…前面 / 旁边、对齐、朝向），由约束求解器（DFS 网格搜索或 MILP）算坐标；硬约束保证不出房间、不相撞 | 代码许可未核实（记得是 Apache-2.0，接入前看 LICENSE）；资产来自 Objaverse，许可混杂 | **正对我们的病**：坐标交给求解器，模型只说关系。可以照它的约束词表和求解器移植 |
| LayoutVLM（2024）、OptiScene（2025，开源模型）、R³L、FirePlace 等 | 同一路线的改进：可微优化、看图校正、相对关系推理 | 多为论文代码 | 后续调优参考；InteriorAgent 指出 Holodeck、LayoutVLM 在复杂房间里摆得乱，需要按场景加规则 |
| Infinigen Indoors（Princeton，CVPR 2024） | Blender 里全程序化生成室内（家具也是程序生成），约束 DSL + 模拟退火 | BSD | 太重（Blender + 程序化资产），现代西式家具为主；有物件重叠、数量对不上的已知问题。不选 |
| blender-mcp（ahujasid，约 3.2 万星） | 让 Claude 等模型通过 MCP 直接操作 Blender（能跑任意 Python） | MIT | 能力强，但还是「模型自己算坐标」，不解决出界；而且要装 Blender、权限大。以后要真渲染时再考虑 |
| SceneCraft（NeurIPS 2024） | 给定布局，生成多视角图再训 NeRF | 论文代码 | 是「布局 → 成图」，不是「文字 → 布局」，不对口 |
| TRELLIS.2（微软）/ Hunyuan3D 2.1（腾讯） | 单个物件文字或图片生成 3D 模型 | TRELLIS.2 MIT；Hunyuan3D 2.1 自有许可（不含欧盟、英国、韩国，月活上限 100 万） | 以后把白模方块换成「八仙桌、柜台」真模型时用；白模阶段不需要 |

**结论**：把白模拆成三层——
1. **房间壳**（墙、地、顶、门窗洞）：程序按 `place.room` 生成，不让模型碰；
2. **布局**：导演只交「放什么、多大、和谁什么关系」，用 Holodeck 那套约束词表，服务端求解器算坐标，硬约束：在房间内、落地或叠在指定部件上、不相撞、不挡门；
3. **资产**：白模阶段用带颜色的方块；以后需要再接 TRELLIS.2 这类 MIT 的单物件生成。

后续：写进契约 §13 的修订，转 DSH。接入 Holodeck 代码前先核实许可。

**群研核实为什么放过错结论（查了审查记录）**：
1. **长页面被截断。** 反驳和核实都去读 ar5iv 上的论文。成本那句在论文靠后的讨论部分，抓回来的文本没到那里。核实的人自己写了「ar5iv 中间章节被截断，无法穷举」，却照样判了通过。
2. **「没找到」也能被盖上「已核实」。** 否定式的结论（某处没有某样东西）要读全了才能下。读不全时应该判「证据不足」，现在的门禁不拦。
3. **两个人不独立。** 反驳和核实用同一个工具读同一个被截断的页面，错法完全一样。「48 分钟」这个错误换算还是反驳的人先提出来的，核实的人照抄了。论文里「1 秒真实 ≈ 1 分钟游戏」是目标速度，实际跑了好几天。
4. 这次运行调了 150 次 web_fetch，这条结论绕过了「先下载原文再读」的路子。研究员按规定不带下载论文的工具。

**为什么群研不如 DSH 单人（翻了两边的会话记录）**：

| | DSH 单人 | 群研 |
|---|---|---|
| 模型 | deepseek-v4.1-flash（经 opencodego） | deepseek-v4-flash（官方），版本低一代 |
| 时长 | 16 分钟 | 20 分钟 |
| 工具调用 | 106 次：web_fetch 66、web_search 19、bash 9 | 569 次：web_fetch 150、web_search 18；提交、审查、发消息、查任务这类协调调用约 280 次，占一半 |
| 读长页面 | 用 bash 跑 curl 把 arXiv 整页拉下来，再用 python 在全文里搜 → 抓到成本那句 | web_fetch 超过约 5 万字就截断，全文存进 `/tmp/dsh-spill…/web_fetch.txt`，提示「用 read 或 grep 去看」。但研究员、反驳、核实都没有 read 和 bash，打不开这个文件。三个人都读到同一个被截断的版本 |
| 谁有 shell | 自己有 | **只有负责人有**（调了 25 次，用来查环境）；真正读资料的人没有，还有 2 次报「unknown tool bash」 |
| 读黑板 | — | research_query 每次返回约 2.3 万字（最多 5 万），上下文被别人的结论占满 |
| 成稿 | 一个脑子从头到尾想，先搭「L0–L7 七层」骨架再填，最后有判断、有 90 天切片 | 按领域分三条路线，各交各的原子结论；没有人负责写贯穿全局的报告，汇总就是把结论分区排好 |

结论：输的不是「多 agent」这个思路，而是四个具体缺陷：
1. **读资料的人工具最少。** 截断以后的全文就在旁边，但打不开。
2. **一半调用花在协调上。**
3. **没有成稿这一步。** 群研擅长逐条较真，不擅长形成观点。
4. **模型低一代。**

**发现的我们的问题**：
- **核实没有真正回到原文。** 核实的人说读了论文全文，却漏了论文里明写成本的那句话，还把它「纠正」成错的。这违背了 MVP-3 的核实规则，要交给 DSH。
- 默认 4 轮就停，还剩一半结论没核实。题目大的时候，追加额度的提示要更早、更显眼。
- 广度不够。漏了几个关键对象（OnlyWorlds、articy、国内带地图的写作工具），说明开局铺的路线不够散。

**对创作台设计的用处**：两边都认同「整条链没人做通」。人物随时间的轨迹、硬性的时空检查、跨作品的设定版本，这三样要自己做。具体结论合进 [prd/16-creative-ux.md](prd/16-creative-ux.md)。
