## B10 推进下一轮（用户 2026-11-03 定）

**改法**：回合结束时的收尾判断不再看「任务是不是都交付了」，改成看**结论的核实情况**。

- 还有候选 / 待核实 / 待反驳 / 有争议 / 证据不足的结论时，服务端推进下一轮（`run.round + 1`，前 2 轮 `independent`、第 3 轮起 `cross`），不因为负责人发了「最终答复」就收尾。
- 提前收尾只认 PRD §3 的三种：**问题已回答且通过核实**（没有未核实的结论，且至少有已核实或负结果）、**剩余路线全部阻塞且没有新机制**、**用户要求结束**。到限（轮数或时长）照旧停。
- 推进时把未核实的结论当**缺口**交回负责人：提示里只给「id + 状态 + 一句话」（最多 12 条）和「这些还没通过独立核实」，**不说第几轮、不教它怎么分轮**，轮次完全由服务端推。
- 第 3 轮起仍附精简 Context Packet（已核实结论 + 明确负结果）。
- `near_limit` 两条触发路径都补上了：时长到 80%（一回合跑得久也照样切，不等回合结束），以及推进到最后一轮（`nextRound >= limit_rounds`）。`report.nextSuggestion` 给「已核实几条、还剩几条没核、剩余缺口、建议追加多少」；**到限停下来之后建议仍然保留**（用户正是看着它决定要不要追加，只有收尾成 `final` 才不再建议）。

## B9 网络抖动不再整条判失败

- 模型转发（`model/messages-proxy.ts`）遇到网络错 / 上游 5xx / 429 时**先重试三次**（400ms、1200ms 退避）；这次请求没拿到任何内容，重发安全。三次都失败才返回 503 `MODEL_UPSTREAM_UNAVAILABLE`（不再伪装成 500 内部错误）。
- 群研运行补丁里加上和探索台同一套 `retryPolicy`（`RATE_LIMIT / SERVER / TIMEOUT / TRANSPORT` 由 DSH 自己重试）。
- 回合仍然失败、且原因是网络类（`fetch failed` / `ECONNRESET` / 5xx / 超时）时：转成 **`paused`** 并写清「模型服务暂时连不上（网络抖动或上游 5xx，已重试过），这一轮停在这里；恢复后点继续就能接着跑」，**不判 `failed`**；失败分支先结算活动时长，**不再清零**。真正的逻辑失败（如 `KERNEL_MAX_TOKENS`）仍判 `failed`。

**真机证据**：运行 `5b52aba2-768c-4317-aa6e-d4801bc69ec3`（档案 `e7462418`）跑到 24 分钟时撞上真实网络抖动（控制面日志里两次 `MODEL_UPSTREAM_UNAVAILABLE: fetch failed`）：运行变成 `paused`、原因就是上面那句、`activeMs` 保留 **1,427,000 毫秒**（旧版本这里是 0 且整条判 failed）。点继续后接着跑，随后正常进到 `near_limit`（「已用 24 分钟 / 30 分钟」）并给出追加建议，最后按用户结束收尾。
