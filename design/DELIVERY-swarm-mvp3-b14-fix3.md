## 做到了的两条

**② 「已送到」只认对方会话里真的出现这条消息**

- 排进收件箱只写 `queued`（新状态），干预写「**已排队**：排进负责人的收件箱，等它取到才算送到」。
- 「已送到」只在投影响应里看到**对方会话的 `user/message` 正文包含这条消息**时才写。
  `agent/inbox/spliced` 不再算送达（它只说明排进了收件箱）——上一版就是在这里误报的。
- 真机验证：运行 `200c6a98` 的加人指令是 `swarm_inbox: lead | instruction | queued | queued:queue:0ae0e730…`，
  干预是 `received`「已排队…」。这次**没有**再出现「已送到」却没送到的情况。

**③ 按卡认人**

- 加人卡批准时把「批准那一刻的名册 id」与卡号一起存进卡。
- 加人指令里写明卡号，并要求负责人建人时把卡号原样带上：
  `research_spawn(..., add_card: <卡号>)` → 插件把 `cardId` 记进成员登记。
- 「已执行」的判定：**只有 `cardId` 等于这张卡号的成员**，或者**该角色人数超过原计划编制**（`plan.roster` 里的人数）才算；
  回执写明是哪个人、哪张卡（例如「已按这张卡（7e31bdd9）建出反驳员 xxx」）。
- 上一版把「批准后新出现的同角色成员」当成按卡建的，而原计划里还没建的人也在批准之后才出现——这条已删掉。
- 单测覆盖：计划内的 critic 出现 → 仍是 `received`；带卡号的第二名 critic → `applied` 且回执带卡号。

## 没做到的一条（卡在运行时）

**① next-step 送不到。** 代码现在按运行时的接口发 `session/prompt` 并带 `mode: "steer"`
（形状 `{ request: { requestId, sessionId, mode, content } }`），运行时回：

```
agent id "undefined" does not match session id "session-1"
```

（来自 `@deepseek-ai/dsh-agent` 的 `agent id "${id}" does not match session id "${agent.session.id}"`。）
失败后自动退回 SDK 自带的 `prompt()`，也就是 **next-turn**。所以现在插话仍然是「下一轮开头就看到」，
不是「下一个步骤」。要做到 next-step，需要运行时接受 SDK 会话的 steer（团队插件内部走的是
`agent.steer(message)`，那条路对 SDK 客户端没开放）。我把这个错误码 `SWARM_STEER_FAILED` 打到日志、把实际模式
记在 `swarm_inbox.reason`（`queued:queue:…` 还是 `queued:steer:…`）里，运行时修好之后不用改代码就能自动切过去。
